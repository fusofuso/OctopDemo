## 0. TL;DR

| 维度 | 结论 |
|------|------|
| 控制面数据库 | **SQLite（WAL）**，单文件 `~/.octop/octop.db`，31 张业务表 |
| 隔离粒度 | **按 agent**。专家是「模板」、agent 是「实例」——不同用户用同一专家默认各自实例化（物理隔离），只有 `is_shared=1` 才共用工作区（详见 §4.1） |
| 短期记忆 | LangGraph checkpoint，**与长期记忆同库**：`agents/<id>/.octop/memory.sqlite` |
| 长期记忆 | octop-memory 结构化记忆，同上文件，表名带 `agent_<id>_` 前缀 |
| 对话历史 | 控制面库的 `thread_messages` / `trajectory_events` 表（v2 归档可选，`history_v2.sqlite`） |
| 用户产出的文件 | `agents/<id>/outbound/`（生成物）、`agents/<id>/inbound/`（上传附件） |
| 用户间是否会串 | **默认不会**（非 owner 读也 403）；但 **`is_shared=1` 的共享 agent 会**——所有用户共用同一工作区 |
| 清除机制 | 删除 **agent** 会连带删工作区；删除 **用户不会**（见 §7 P1） |

## 1. 存储总览

Octop 的持久化分成 **5 个 SQLite 文件 + 文件系统**：

| # | 文件 | 作用 | 生命周期 |
|---|------|------|---------|
| 1 | `~/.octop/octop.db` | **控制面**：用户、agent、会话、渠道、审计… | 安装时创建 |
| 2 | `~/.octop/agents/<id>/.octop/memory.sqlite` | **短期记忆（checkpoint）+ 长期记忆** | agent 首次运行时创建 |
| 3 | `~/.octop/knowledge/<kb_id>/index.sqlite` | 知识库分块向量索引 | 启用知识库时创建 |
| 4 | `~/.octop/history_v2.sqlite` | 分段历史归档（**默认关闭**） | 开启 `history_v2_enabled` 时创建 |
| 5 | `~/.octop/agents/<id>/.octop/checkpoints.sqlite` | ⚠️ **本项目不使用**——harness 默认路径，被 octop-memory 的 checkpointer 取代 | — |

> **重要更正**：很多资料（含 harness 自带注释 `octop_harness/agent.py:1777,1799`）描述 checkpoint 落在 `{workspace}/checkpoints.sqlite`。但 Octop 通过 octop-memory 注入了自己的 `CompactSqliteSaver`（`infra/agents/memory/slim.py:63-82` 从 `memory._checkpointer` 取），**实际把 checkpoint 写进 `memory.sqlite`**。实测目录下只有 `memory.sqlite`。

其余持久化内容不在 SQLite：

| 内容 | 位置 |
|------|------|
| JWT 密钥 | `~/.octop/secrets/jwt_secret`（文件） |
| 人格 / 工作区文件（`SOUL.md`、`USER.md`…） | `~/.octop/agents/<id>/` |
| Agent 级环境变量 | `agents/<id>/.octop/.env` |
| 全局环境变量 | `~/.octop/env`（dotenv） |
| 日志 | `~/.octop/logs/`（轮转 + 14 天保留） |
| CLI 状态 | `~/.octop/cli_state.json` |
| 备份归档 | `~/.octop/backups/` |

### 2.2 两个容易混淆的点

**`sessions` 不是登录会话。** 它是"渠道会话 → 线程"的映射表：

```sql
-- 001_initial.sql
CREATE TABLE sessions (
  session_key TEXT NOT NULL UNIQUE,   -- 如 <aid>:dashboard:<uid>:dm
  agent_id    TEXT NOT NULL,
  user_id     INTEGER NOT NULL,
  channel_type TEXT NOT NULL,
  thread_id   TEXT NOT NULL,
  unread_count INTEGER NOT NULL DEFAULT 0,
  ...
);
```

登录态由 JWT 承载，密钥在**文件** `~/.octop/secrets/jwt_secret`，不在数据库。

**`users_new` / `knowledge_documents_legacy` / `knowledge_base_members` 是迁移中间表或已废弃表。** 例如 `knowledge_base_members` 在 `007_resource_identity_and_profile.sql:20` 被 `DROP TABLE IF EXISTS` 显式删除。生产库中不应期望看到它们。

### 2.3 运行参数

```48:49:src/octop/infra/db/pool.py
        self._conn.execute("PRAGMA foreign_keys = ON")
        self._conn.execute("PRAGMA journal_mode = WAL")
```

- `foreign_keys = ON` → **级联删除生效**（这对 §7 P1 很关键）
- `journal_mode = WAL` → 伴随 `-wal` / `-shm` 文件；直接拷贝 `.db` 可能丢数据，备份请用 `octop backup`

## 3. 记忆机制

### 3.1 三层必须区分开

这是最容易误解的地方——**对话历史、短期记忆、长期记忆是三套独立的东西**：

```
┌────────────────────────────────────────────────────────────────┐
│ 对话历史（用户可见）                                             │
│   控制面 octop.db: thread_messages / trajectory_events          │
│   → 支撑 Dashboard 的列表、分页、导出、分叉                       │
└────────────────────────────────────────────────────────────────┘
┌────────────────────────────────────────────────────────────────┐
│ 短期记忆（模型上下文）                                           │
│   agents/<id>/.octop/memory.sqlite → checkpoints / writes 表    │
│   → LangGraph 线程状态，决定模型"记得"什么                        │
└────────────────────────────────────────────────────────────────┘
┌────────────────────────────────────────────────────────────────┐
│ 长期记忆（跨会话沉淀）                                           │
│   agents/<id>/.octop/memory.sqlite → agent_<id>_* 表            │
│   → octop-memory 的结构化记忆与全文索引                          │
└────────────────────────────────────────────────────────────────┘
```

**删一处不会清另一处。** 例如删除会话时清理的是 checkpoint（短期），`thread_messages` 与长期记忆各自独立处理。

### 3.2 对话历史

| 项 | 说明 |
|---|------|
| 默认载体 | 控制面库的 `thread_messages`（消息正文投影）+ `trajectory_events`（轨迹） |
| 投影状态 | `thread_history_projection` 记录投影进度 |
| 分页 | 返回 `next_cursor`，客户端应原样使用（不要用 offset 替代） |
| 导出 | `GET /api/agents/{agent_id}/threads/{thread_id}/history/export` |
| 保留裁剪 | **轨迹事件**每线程保留最近 **50** 个用户轮次（`history/trajectory/settings.py:21`、`trajectory/service.py:253-255`） |
| v2 归档 | 开启 `history_v2_enabled` 后，**新回合**写入 `~/.octop/history_v2.sqlite`；旧回合仍在主库，靠兼容读取接口按段拼接 |

**v2 归档的表结构**（`infra/history/store.py:25-50`）：

| 表 | 作用 |
|---|------|
| `archive_meta` | 版本 + 控制面身份指纹（跨机/换路径恢复会校验） |
| `segments` | 会话内的归档分段（legacy ↔ v2 边界） |
| `turns` | 回合状态（active / paused / complete / partial / failed / interrupted） |
| `documents` | 消息或轨迹的结构文档 |
| `bodies` | **按内容哈希共享的正文**（消息、可见 thinking、工具参数/结果） |
| `body_refs` | 文档 ↔ 正文的引用关系 |

价值在于**正文去重**：同一条长文本被消息视图和轨迹视图引用时只存一份。

**限制**：
- 仅支持 **SQLite 主库**，PostgreSQL 开启会被明确拒绝启动（`versioned-history.md:38`）
- 落地文件旁边有 `history_v2.required` 标记，**不可单独删除其中一个**
- 不能退回到"不认识 v2"的旧程序

### 3.3 短期记忆（checkpoint）

| 项 | 说明 |
|---|------|
| 载体 | `agents/<id>/.octop/memory.sqlite` 的 `checkpoints` / `writes` / `hm_checkpoint_blobs` 表 |
| 实现 | octop-memory 的 `CompactSqliteSaver`（`infra/agents/memory/slim.py:63-64`） |
| 位置 | **本地工作区内，与控制面数据库无关**——即使控制面换成 PostgreSQL 也留在本地（`architecture.md:129-131`） |
| 删除 | 删除会话时调用 `delete_thread_checkpoint`（`agents/manager.py:1140-1169`） |
| 维护 | `memory slim` 可对活跃 checkpoint 做瘦身（`infra/agents/memory/slim.py`） |

**实证**（附录 A 样本）：`checkpoints` 69 行、`writes` 106 行、`hm_checkpoint_blobs` 1 行。

> 注意 `delete_thread_checkpoint` 的注释明确警告：只删 `thread_registry` 行会让"删除会话"变成**表面删除**，内容永远留在 checkpoint store 里。

### 3.4 长期记忆（octop-memory）

同一文件内，表名统一带 `agent_<id>_` 命名空间前缀：

| 表 | 作用 |
|---|------|
| `memory_nodes` | 记忆节点（核心） |
| `atoms` / `candidates` | 记忆原子与候选（抽取阶段） |
| `entities` / `entity_pages` | 实体与实体页 |
| `episodes` / `digests` | 情节与摘要 |
| `raw_events` / `journal` | 原始事件与日志 |
| `aliases` / `meta` / `thread_active_entities` | 别名、元信息、线程活跃实体 |
| `*_fts` / `*_fts_data` / `*_fts_idx` / `*_fts_config` / `*_fts_docsize` | 各表的 FTS5 全文索引 |

后端选择逻辑（`infra/agents/memory/backend.py:13-65`）：

| 控制面 | 记忆默认落点 |
|--------|-------------|
| SQLite | `agents/<id>/.octop/memory.sqlite`（文件） |
| PostgreSQL | **跟随同一 DSN**，每个 agent 一个 `agent_<id>` schema |

想在使用 PostgreSQL 控制面时保持文件记忆，需在 agent 配置显式声明：

```json
"memory": { "backend": { "type": "sqlite" } }
```

也支持 `{"type": "postgres", "dsn": "…"}` 指向独立实例。

> ⚠️ **没有自动的 SQLite → PostgreSQL 记忆数据迁移**（`configuration.md:200`）。

### 3.5 记忆的命名空间

`open_memory_kwargs` 返回 `namespace = f"agent_{agent_id}"`（`memory/backend.py:76`）。所以**同一份记忆文件可以通过前缀区分多租户**，但 Octop 当前是**一 agent 一文件**，前缀只是与 octop-memory 的通用约定对齐。

## 4. 工作空间机制

### 4.1 隔离粒度：按 agent

这是整个设计的核心：**工作空间属于 agent，不属于用户，也不属于会话**。

```
~/.octop/agents/<agent_id>/          ← 隔离边界
```

一个用户可能有多个 agent。**同一 agent 下的所有会话共享同一个工作目录。**

> ⚠️ 这一节最容易产生误解，务必先分清两个概念——「专家」和「agent」不是一回事。

**专家（expert）是模板，agent 是实例。** 权威定义：

```1:8:src/octop/infra/agents/experts/catalog.py
"""Expert catalog — bundled "scene templates" inherited from finnie.

An *expert* is metadata in ``manifest.json`` plus files on disk under
``library/<id>/``. At seed time files (including a copy of ``manifest.json``)
are written into the agent workspace under ``.octop/manifest.json``.
```

| 概念 | 是什么 | 位置 |
|------|--------|------|
| **专家（expert / 模板）** | 一套**静态模板**：`manifest.json` + 提示词 + 技能文件 | `infra/agents/experts/library/<id>/`（只读，启动时扫描） |
| **agent（实例）** | 用户从模板**实例化**出来的活对象，有独立 workspace | `~/.octop/agents/<agent_id>/` |

**「隔离粒度按 agent」的准确含义**：文件隔离的最小单元是 **agent**（一个 `agents/<agent_id>/` 目录）。系统**不会**按用户或会话再往下分目录——一个 agent 的 workspace 就是一块完整的、不与他人共享的地；但**这块地内部**（无论多少会话、多少人在用）的东西都堆在一起。

#### 4.1.1 隔离靠「实例化」，不靠权限过滤

**关键结论：不同用户"用同一个专家"，几乎总是"同一套模板的多个独立实例"，而不是"同一个共享对象"。**

创建流程（`infra/agents/manager.py:599-605, 673-674`）每次都：

1. 生成唯一 `agent_id`
2. `seed_workspace_dir_on_create` → 各自独立的 workspace 目录
3. `_seed_expert_template` → 把模板文件**复制一份**进自己的 workspace

所以用户甲、乙都从专家库选"小办·办公自动化"，得到的是：

| | 用户甲 | 用户乙 |
|---|---|---|
| agent_id | `AAA` | `BBB` |
| workspace | `~/.octop/agents/AAA/` | `~/.octop/agents/BBB/` |
| 模板来源 | 同一份 `library/office-automation/` | 同一份 |
| 文件 / 记忆 / 会话 | 完全独立 | 完全独立 |

**隔离的本质是物理分离，而不是"同一份数据靠权限挡着"。** 权限校验（§5.1）只是第二道防线，防止用户越权访问**别人**的 agent。

#### 4.1.2 三种"共享"场景对照

| 场景 | 触发方式 | 会话列表 | 文件 | 记忆 |
|------|---------|:---:|:---:|:---:|
| 各自实例化（**默认**） | 各用户从专家库/市场创建自己的 agent | ✅ 隔离 | ✅ 隔离 | ✅ 隔离 |
| 共享 agent | 某用户设 `is_shared=1`，其他用户直接使用**同一个 agent** | ✅ 隔离（`threads.user_id`） | ❌ **共享**（同一 `outbound/`） | ❌ 共享（同一 `memory.sqlite`） |
| 团队（AgentTeams） | 协调者 + 成员 agent | ✅ 各成员用自己的 thread/checkpoint | ⚠️ 落在各成员 agent 自己的 workspace | ⚠️ 各成员独立 |

**要点**：

- 只有 `is_shared=1` 才是"多用户共用一个 agent 实例"，此时**会话隔离、文件不隔离**（对应 §7 P3）。
- 团队模式下，成员页用的是成员自己的 thread/checkpoint（`agents/teams/team_manager.py:7-8`），文件仍在各自成员 agent 的 workspace 里。

#### 4.1.3 实例化后与模板脱钩

因为隔离靠"复制快照"，**从专家库建 agent 之后就不再和模板同步**：

- 内置专家模板更新了，已创建的 agent **不会**跟着变（除非重建或重新 seed）
- 用户 A 发布专家，用户 B 基于**快照**（`published_experts`）创建独立实例，之后 A 改了自己的 agent，B 的也不受影响

这也解释了为什么隔离边界要定在 agent 这一层——agent 实例化的那一刻起，它的 workspace 就是一个自包含的、独立的世界。

| 产物识别 | 正则从句子里提取 `(?:outbound|inbound|generated)/...`（`infra/agents/threads/artifact.py:46`） |
| 保护前缀 | `_builtin_skills` 及其 `.octop/_builtin_skills` 变体拒绝修改（`api/routers/workspace.py:37,46-52`） |

**没有按会话分子目录**——同一 agent 的多个会话生成的文件都在同一个 `outbound/`，靠时间戳前缀避免重名。

### 4.4 三种 backend 形态

| 形态 | 触发 | 磁盘位置 | agent 看到的路径 |
|------|------|---------|----------------|
| **host-rooted**（默认） | 不指定 `root_dir` | `~/.octop/agents/<id>/` | 宿主虚拟路径 |
| **scoped / jail** | 显式设 `root_dir` | `{root_dir}/.octop/workspaces/<id>/` | `/.octop/workspaces/<id>` |
| **named / remote** | 在控制台建 `storage_backends` 记录并引用 | COS/S3/PostgreSQL/Docker | 由后端决定 |

默认解析（`infra/backend/resolver.py:12-31`）：没有 `backend` 配置时返回 harness 的 `DEFAULT_BACKEND_SPEC`（host-rooted）。

远程后端需要显式引用才生效：

```json
{ "backend": { "type": "named", "name": "<storage_backends.name>" } }
```

也可以组合（`composite` + `routes`），按路径前缀把不同目录挂到不同后端。

### 4.5 路径解析规则

`workspace_dir` 与 `backend.root_dir` 是**两个维度**（`workspace/dir.py:3-8`）：

- `root_dir` —— 本地后端的根（agent 可见的 `/`）
- `workspace_dir` —— agent 的工作目录，DB 中的值就是权威值，harness 原样接收

创建时若未指定（`dir.py:96-121`）：

| backend 形态 | 磁盘路径 | 持久化值 |
|-------------|---------|---------|
| host-rooted | `{OCTOP_HOME}/agents/<id>/` | 宿主绝对路径 |
| scoped | `{root_dir}/.octop/workspaces/<id>/` | agent 面向路径 `/.octop/workspaces/<id>` |

用户显式指定的 `workspace_dir` 永远优先。

## 5. 隔离与安全

### 5.1 访问控制矩阵

`api/common/agent.py` 定义了三条判定：

```14:31:src/octop/api/common/agent.py
def user_owns_agent(row: Any, user: Any) -> bool:
    return row.user_id is not None and row.user_id == user.id

def assert_agent_owner(row: Any, user: Any) -> None:
    """Raise if the user may not mutate this agent row (admin bypasses)."""
    if user.is_admin:
        return
    if row.user_id is None or row.user_id != user.id:
        raise OctopError(ErrorCode.FORBIDDEN, "agent not owned by user")

def _user_may_access(row: Any, user: Any) -> bool:
    if user.is_admin:
        return True
    if row.user_id is not None and row.user_id == user.id:
        return True
    return bool(agent_is_shared(row))
```

| 操作 | 允许者 |
|------|--------|
| **写**（改配置、删除） | owner 或 admin |
| **读 / 使用** | owner、admin、**或任意用户（当 `is_shared=1`）** |

### 5.2 共享 agent 的语义与风险

| 场景 | 文件是否互见 |
|------|------------|
| 各用户各自的 agent（`is_shared=0`） | ✅ 否。非 owner 读也是 403 |
| 共享 agent（`is_shared=1`） | ⚠️ **是**。所有用户访问同一 `outbound/` / `inbound/` |

注意差异：

- **会话列表按用户隔离**——`threads.user_id` 存在，用户只看到自己的会话
- **文件不隔离**——工作区是 agent 级的

这是"团队共享工作区"的设计语义（共享 agent 用于协作场景），但**对"多人各用各的文档"场景会造成数据互见**。

### 5.3 资源策略（`resource_policy`）

`infra/users/resource_policy.py` 支持按用户下发三类策略：

| 策略 | 作用 | 备注 |
|------|------|------|
| `workspace_root_dir` | 把该用户的 agent 本地工作区**锁定在指定目录内** | 越界即拒（`:160-179`）；**容器部署下不可用**（`:110-122`） |
| `token_quota` | token 用量上限 | 超限抛 `TOKEN_QUOTA_EXCEEDED` |
| `max_agents` | agent 数量上限 | 超限抛 `AGENT_QUOTA_EXCEEDED` |

`assert_backend_within_user_root` 会校验 agent 的 backend 根目录是否落在策略目录内，是防止用户把工作区指到别人目录的主要手段。

**注意：没有磁盘容量配额**（见 §7 P5）。

### 5.4 更强隔离：scoped workspace

给 agent 显式设 `root_dir`（例如指向一个 bwrap jail），工作区就落到 `{root_dir}/.octop/workspaces/<id>/`，agent 面向 `/.octop/workspaces/<id>`。配合 `infra/utils/bwrap.py` 可把执行环境整体关进沙箱。

另外 `execute_env.py` 还会为 scoped 模式注入 agent 面向路径的 `OCTOP_AUTH_DIR` / `OCTOP_SKILLS_DIR`（`workspace/execute_env.py:33-65`），保证 jail 内路径一致。

## 7. 当前存在的问题

按严重度排序。前两项目前是**确凿的缺陷**，其余为设计取舍或能力缺口。

### P1 · `删除用户不清理 agent 工作区`（严重）

**现象**：`UserManager.remove()` 只删除 `~/.octop/users/<username>/`，然后删数据库行。

```756:769:src/octop/infra/users/manager.py
    async def remove(self, username: str) -> None:
        row = self._services.user_repo.get_by_username(username)
        if row is None:
            raise OctopError(ErrorCode.NOT_FOUND, "user not found")
        async with self._lock:
            self._users.pop(username, None)
        user_dir = self._services.paths.user_dir(row.username)
        try:
            if user_dir.exists():
                shutil.rmtree(user_dir)
        except OSError:
            logger.exception("rmtree failed for %s; user removed from DB anyway", user_dir)
        self._services.user_repo.delete(row.id)
        self._services.audit_repo.write(actor=ACTOR_ADMIN, action="user.delete", target=username)
```

而 `agents` 表的外键是级联删除：

```sql
-- 001_initial.sql
user_id  INTEGER REFERENCES users(id) ON DELETE CASCADE
```

**后果**：

1. **数据库行被级联删除**（因为 PRAGMA `foreign_keys = ON`）
2. **文件系统目录留下**：`~/.octop/agents/<agent_id>/` 变成**孤儿**，失去所有访问入口
3. 影响面：磁盘泄漏；更严重的是**合规风险**——"删除用户"后其对话产物（PPT/Word）、记忆库、checkpoint 仍完整留在磁盘上，且无法通过 UI 找回或清理

**三条路径都如此**（均已核对源码）：

| 路径 | 额外清理 | 证据 |
|------|---------|------|
| `UserManager.remove()` | 只 `rmtree(users/<username>/)` | `infra/users/manager.py:756-769` |
| `DELETE /api/users/{user_id}` | 额外删头像，**仍不碰工作区** | `api/routers/users.py:541-555` |
| 用户批量操作 `delete` | 直接转发到 `remove()` | `api/routers/users.py:354-355` |

底层仓储确认是**纯删行**，没有任何文件系统副作用：

```337:339:src/octop/infra/db/repos/users.py
    def delete(self, user_id: int) -> None:
        with self._db.transaction() as conn:
            conn.execute("DELETE FROM users WHERE id = ?", (user_id,))
```

**对比**：`AgentManager.delete_agent()` 是有 `rmtree(workspace_dir)` 的（`agents/manager.py:873-877`）。差别在于删除用户路径上没有遍历其名下 agent。

**复现方式**：建一个测试用户 → 在其名下创建一个 agent 并对话生成文件 → 删除该用户 → 检查 `~/.octop/agents/` 下该 agent 目录是否仍在（预期：仍在）。

**修复方向**：`remove()` 中先查出该用户名下的 agent（`agent_repo.count_by_user` / 对应的 list 方法），逐个执行与 `delete_agent` 相同的清理（或复用同一内部方法），再删用户行。

---

### P2 · `删除会话不清理该会话的产物文件`（中高）

**现象**：`delete_thread_checkpoint` 只清 checkpoint 数据（`agents/manager.py:1140-1169`），`outbound/` 里该会话生成的 PPT/Word **永久残留**。

**后果**：用户在 UI 里"删除对话"后，磁盘上文件仍在；对共享 agent 场景，其他用户仍能在工作区里看到这些文件。

---

### P3 · `共享 agent 的工作区没有隔离`（中高）

**现象**：`is_shared=1` 时 `_user_may_access` 对所有用户返回 True（`api/common/agent.py:26-31`），而工作区是 agent 级的。

**后果**：多个用户使用同一个共享 agent，A 上传/生成的文档对 B 可见。会话列表是隔离的，**文件不是**——容易造成"以为隔离了"的错觉。

**可选方向**：为共享 agent 提供 per-user 子目录（如 `outbound/<user_id>/`）、只读共享、或"共享但产物私有"三种模式。

---

### P4 · `outbound/` 缺少保留策略，磁盘单调增长（中）

**现象**：轨迹有 50 轮裁剪、日志有 14 天保留、备份有滚动，但**用户产出文件没有任何 retention**。

**后果**：长期运行的实例，`outbound/` 只增不减；尤其浏览器截图的 `outbound/screenshots/` 会快速堆积。

**可选方向**：按时间/总大小/单 agent 配额的清理策略；或提供"清理 N 天前产物"的运维入口。

---

### P5 · `缺少磁盘容量配额`（中）

**现象**：`resource_policy` 提供 `token_quota` 与 `max_agents`，但**没有磁盘用量配额**。

**后果**：单个 agent（或共享 agent 的任一用户）可以写满磁盘，影响整个实例。没有超限告警。

**可选方向**：统计各工作区用量并纳入策略；超限时拒绝写入或告警。

---

### P6 · `checkpoint 与长期记忆同库`（中）

**现象**：短期记忆（`checkpoints` / `writes`）与长期记忆（`agent_<id>_*`）共用一个 `memory.sqlite`。

**后果**：

- **写放大明显**：实证样本中主库 770 KB，但 `-wal` 达 2.6 MB（checkpoint 是高频写入）
- 故障域合并：库损坏会同时损失会话状态与长期记忆
- 维护耦合：`memory slim`（瘦身 checkpoint）与记忆数据在同一文件上竞争锁
- 备份粒度无法分开：想只备份记忆就必须连 checkpoint 一起备份

**可选方向**：拆成两个文件（或让 `CompactSqliteSaver` 的路径可配置），至少在配置层允许分离。

---

### P7 · `history_v2 仅支持 SQLite`（低）

**现象**：`versioned-history.md:38` 明确"PostgreSQL 开启此功能会明确拒绝启动"。

**后果**：使用 PostgreSQL 控制面的部署无法获得分段归档（正文去重、按段分页）能力。

---

### P8 · `缺少 SQLite → PostgreSQL 的记忆迁移工具`（低）

**现象**：`configuration.md:200` 明确"no automatic SQLite→PG memory data migration"。

**后果**：控制面迁移到 PG 时，历史记忆需要人工处理；切回文件记忆同样无工具。

---

### P9 · `同一 agent 内多会话文件不分目录`（低）

**现象**：所有会话的产物都在同一个 `outbound/`，仅靠 `{unix_ts}_` 前缀区分。

**后果**：人工排查"哪个文件属于哪次对话"困难；文件数多时目录膨胀。

---

### P10 · `迁移中间表残留风险`（低）

**现象**：迁移流程中会创建临时表（`users_new`、`knowledge_documents_legacy`），依赖后续迁移显式 `DROP`（如 `007_...sql:20` 删除 `knowledge_base_members`）。

**后果**：若某次迁移中断或 `DROP` 遗漏，会产生无用表占用空间并干扰运维排查。
