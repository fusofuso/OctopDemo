# 知识库：从上传到检索的完整链路

一份文档从上传到被模型引用，中间经历了哪些步骤、数据落在哪里、对话时怎么被选中和检索。

> **基线**：`1.0.2b4`（`origin/main` = `232030f4`）

## 0. 全流程一图

```
① 上传            POST /api/knowledge-bases/{kb_id}/documents
                     │  校验：权限、大小、扩展名、OCR 开关
                     ▼
② 落盘            ~/.octop/knowledge/<kb_id>/docs/<doc_id><后缀>
                  控制面 DB 记一行 knowledge_documents（status=pending）
                     │
③ 入队            enqueue_index_document(...)   信号量并发 2
                     ▼
④ 解析            parse_document()  按扩展名分派（PDF/DOCX/PPTX/XLSX/HTML/CSV/纯文本/图片OCR）
                     ▼
⑤ 分片            chunk_text(text, size=800, overlap=120)
                     ▼
⑥ 嵌入            embed_knowledge_texts()   onnx 本地模型 或 remote API
                     ▼
⑦ 建索引          ~/.octop/knowledge/<kb_id>/index.sqlite  → chunks 表（原子替换）
                  控制面 DB: status=ready, chunk_count=N
──────────────────────── 以上是写入侧；以下是每次对话的读取侧 ────────────────────────
⑧ 选库            default_open / Dashboard 显式指定 / agent 专家级配置  → 合并出本轮 KB 列表
                     ▼
⑨ 注入 config     request["configurable"]["knowledge_base_ids" + "knowledge_base_catalog"]
                     ▼
⑩ 改工具描述      KnowledgeSearchHintMiddleware 把库名/描述写进 search_knowledge 的 description
                  （catalog 为空则直接摘除该工具）
                     ▼
⑪ 模型决定调用    search_knowledge(query, k)
                     ▼
⑫ 检索            embed(query) → 逐库余弦相似度 top-k → 全局合并排序
                     ▼
⑬ 格式化          ［引用标记］+ 正文，受 6000 字符预算限制
                     ▼
⑭ 进入对话        作为工具结果返回给模型
```

## 1. 阶段一：上传与落盘

### 1.1 入口

| 操作 | 端点 | 说明 |
|------|------|------|
| 上传文件 | `POST /api/knowledge-bases/{kb_id}/documents` | `UploadFile` + 可选 `path`（嵌套目录） |
| 新建 md/txt | `POST /api/knowledge-bases/{kb_id}/documents/text` | 直接给文本内容 |
| 编辑 md/txt | `PUT /api/knowledge-bases/{kb_id}/documents/{doc_id}` | 覆盖内容并标记重索引 |
| 单文档重索引 | `POST .../documents/{doc_id}/reindex` | 状态回到 `pending` |
| 整库重索引 | `POST /api/knowledge-bases/{kb_id}/reindex` | 批量 |

所有写操作在成功后都会调用 `enqueue_index_document(...)`（`api/routers/knowledge_bases.py:712,750,853,925,956`）。

### 1.2 校验链

`KnowledgeService.upload_document`（`infra/knowledge/service.py:347-391`）依次校验：

| 校验 | 规则 |
|------|------|
| 功能可用 | `assert_knowledge_usable(...)` —— **没配 embedding 模型直接拒绝**（见 §4） |
| 写权限 | `get_writable_base` —— owner 或 admin（`shared` 只给读） |
| 大小 | `max_upload_mb`，默认 100 MiB（`config.py` 的 `DEFAULT_MAX_UPLOAD_MB`） |
| 图片需 OCR | 图片后缀且 OCR 未启用 → 拒绝（`service.py:369-373`） |
| 内容类型 | 必须在白名单 `_ALLOWED_CONTENT_TYPES` 内 |
| 文档数 | 按库的 `max_documents`，默认 `MAX_DOCS_PER_KB = 100`；单用户最多 `MAX_BASES_PER_OWNER = 20` 个库 |

## 2. 阶段二：解析

`parse_document(path, ocr=...)`（`infra/knowledge/parse.py:32-71`）**按扩展名分派**：

| 扩展名 | 解析方式 |
|--------|---------|
| `.md` `.markdown` `.txt` `.rst` `.yaml` `.yml` `.jsonl` | 直接读；**编码依次尝试 UTF-8-BOM → GB18030**（避免 GBK 中文变乱码） |
| `.json` | 解析后美化输出，失败则原文 |
| `.html` `.htm` | `HTMLParser` 提取文本，跳过 `script/style/noscript/template`，块级标签换行 |
| `.csv` / `.tsv` | 按分隔符转成「`# 表名` + 制表符分隔行」 |
| `.pdf` | `pypdf` 逐页 `extract_text()`；**文本为空且有 OCR 时回退 OCR** |
| `.docx` | `python-docx`，但**不用** `Document.paragraphs`（会漏表格/文本框/修订包裹），而是遍历 `w:p` 与 `w:altChunk` |
| `.pptx` | `python-pptx`，逐 slide 逐 shape 取 `text` |
| `.xlsx` `.xlsm` | `openpyxl` 只读模式，逐 sheet 转文本 |
| `.xls` | `xlrd`（含日期单元格格式化） |
| 图片（`.png` `.jpg` `.jpeg` `.webp`） | **OCR**（需启用，见 §9） |

`def _parse_docx` 有个值得一提的设计（`parse.py:110-129`）：遍历 `w:p` 和 `w:altChunk` 两种节点，跳过 `mc:Fallback`（避免重复），并展开 `altChunk` 引用的嵌入 HTML/Word 部件——因为部分转换器把正文留在嵌入部件里。

## 3. 阶段三：分片

核心逻辑非常简洁（`infra/knowledge/chunk.py`）：

```6:21:src/octop/infra/knowledge/chunk.py
def chunk_text(text: str, *, size: int = 800, overlap: int = 120) -> list[str]:
    """Split non-empty text into stable overlapping character windows."""
    ...
    step = size - overlap
    chunks: list[str] = []
    for start in range(0, len(content), step):
        chunks.append(content[start : start + size])
        if start + size >= len(content):
            break
    return chunks
```

要点：

| 项 | 说明 |
|----|------|
| 默认窗口 | **800 字符**，重叠 **120 字符**，步长 680 |
| 切分依据 | **纯字符窗口**——不按句子、段落或语义边界 |
| 是否支持 Markdown 结构 | ❌ 不识别标题层级，标题可能被切断 |
| 可配置 | `knowledge_chunk_size`（100–8000）、`knowledge_chunk_overlap`（0 到 size-1） |
| 调参影响 | **改 `chunk_size` / `chunk_overlap` 后，已索引的文档不会自动重分片**——需要触发重索引 |

参数解析在 `infra/knowledge/params.py:48-79`（`get_advanced_settings`），越界值会回落到默认值而不是报错。

## 4. 阶段四：嵌入

`embed_knowledge_texts(services, texts)`（`infra/knowledge/embed.py:17-38`）按设置分两条路：

| 后端 | 设置值 | 实现 |
|------|--------|------|
| **本地 ONNX**（默认） | `knowledge_embedding_backend` = `onnx` | `onnx_service.embed_texts(model, texts)` —— 本地推理，无需外网 |
| **远程 API** | `remote` | 走 provider 的 `/embeddings`（OpenAI 兼容） |

远程路径的细节：

- 从 `provider_repo` 取 base_url / api_key，缺任一则抛 `knowledge remote embedding provider is not ready`
- **批量上限 20 条/请求**（`_KNOWLEDGE_EMBEDDING_BATCH_LIMIT`），按顺序切片保证向量与文本对齐
- 返回数量不匹配会报错（`embedding count mismatch`）

维度记录：首次索引成功后，把向量维度写进 `knowledge_bases.embedding_dim`（`jobs.py:54-57`）。

> **换模型的后果**：不同模型的向量维度不同。检索时若 `len(embedding) != len(query)`，该 chunk 会被**静默跳过**（`index.py:115-116`）。所以换 embedding 模型必须走 `reindex_all_documents`。

## 5. 阶段五：索引存储

### 5.1 落盘位置与表结构

每个知识库**一个独立的 SQLite 文件**（与知识库内容同目录）：

```
~/.octop/knowledge/<kb_id>/index.sqlite
```

表结构（`infra/knowledge/index.py:40-55`）：

```sql
CREATE TABLE IF NOT EXISTS chunks (
    chunk_id  TEXT PRIMARY KEY,
    doc_id    TEXT NOT NULL,
    ordinal   INTEGER NOT NULL,
    text      TEXT NOT NULL,
    embedding BLOB NOT NULL,        -- float32 数组的二进制
    meta_json TEXT NOT NULL DEFAULT '{}'
);
CREATE INDEX IF NOT EXISTS idx_chunks_doc ON chunks(doc_id);
```

| 列 | 含义 |
|----|------|
| `chunk_id` | 分片主键 |
| `doc_id` | 所属文档（用于按文档批量替换/删除） |
| `ordinal` | 分片在该文档内的序号（引用时显示"第 N 段"） |
| `text` | 分片原文 |
| `embedding` | `struct.pack` 的 float32 向量 |
| `meta_json` | 附加元数据 |

### 5.2 写入是原子替换

```86:92:src/octop/infra/knowledge/index.py
        with self._connect() as conn:
            conn.execute("DELETE FROM chunks WHERE doc_id = ?", (doc_id,))
            conn.executemany(
                "INSERT INTO chunks(chunk_id, doc_id, ordinal, text, embedding, meta_json) "
                "VALUES (?, ?, ?, ?, ?, ?)",
                rows,
            )
```

同一事务内先删后插，所以**重新索引过程中不会出现"半新半旧"**。

### 5.3 文档状态机

| 状态 | 含义 |
|------|------|
| `pending` | 已上传，等待索引（重启后由 `resume_pending_index_jobs` 恢复） |
| `processing` | 索引中 |
| `ready` | 可被检索（**检索只认这个状态**） |
| `failed` | 索引失败，`error_message` 存原因，`chunk_count` 归零 |

### 5.4 调度

- 索引跑在**线程池**里（`loop.run_in_executor`），不阻塞事件循环
- 并发上限 `INDEX_CONCURRENCY = 2`（进程级信号量）
- 进程重启后 `resume_pending_index_jobs(services)` 重新入队未完成的文档（`jobs.py:82-86`）

## 6. 阶段六：对话时如何选中知识库

这是"去哪个库检索"的答案——**每轮对话开始时先算出本轮挂载哪些库**。

### 6.1 三个来源

| 来源 | 说明 |
|------|------|
| **Dashboard 显式指定** | 对话请求带 `knowledge_base_ids`（`api/routers/chat/models.py:89-91`） |
| **用户 `default_open` 偏好** | 该用户自己的、标记为默认打开的知识库 |
| **agent 专家级配置** | agent `config_json.knowledge_base_ids`（创建/编辑专家时选的） |

### 6.2 合并规则

```11:35:src/octop/infra/knowledge/default_open.py
def merge_knowledge_base_ids(
    visible_bases: Sequence[KnowledgeBaseRow],
    explicit_ids: list[str] | None,
    *,
    owner_user_id: int,
    extra_ids: Sequence[str] | None = None,
) -> list[str]:
    """Use the actor's own default-open bases when a turn omits a list.

    ``default_open`` is per-owner preference: shared bases marked default-open
    are auto-injected only for the creating user, not for other viewers.
    ``extra_ids`` (expert composer picks) are unioned in when still visible.
    """
    if explicit_ids is not None:
        return list(explicit_ids)
    selected: list[str] = []
    visible_ids = {base.id for base in visible_bases}
    for base in visible_bases:
        if base.default_open and int(base.owner_user_id) == int(owner_user_id):
            selected.append(base.id)
    for kb_id in extra_ids or []:
        text = str(kb_id).strip()
        if text and text in visible_ids and text not in selected:
            selected.append(text)
    return selected
```

规则总结：

| 情况 | 结果 |
|------|------|
| `explicit_ids is not None` | **完全采用显式列表**，不做 `default_open` 注入 |
| `explicit_ids == []` | 本轮**不使用任何知识库**（Dashboard 的 opt-out 手段） |
| `explicit_ids is None` | `本用户 default_open 的库` ∪ `agent 专家级 extra_ids`（仅限仍可见的） |

两个易踩的点：

- **`default_open` 是按 owner 的**：一个被共享的库即使标记了 `default_open`，也**只对创建者自动注入**，其他使用者不会自动挂上（`default_open.py:20-21`）
- **显式传 `[]` 与不传是两回事**：传空数组表示"本轮不要知识库"，不传才会走默认注入。代码注释里也特意注明 `Including [] — Dashboard opt-out`（`api/routers/chat/turn.py:325`）

### 8.1 工具调用与上下文读取

### 8.2 检索流程

`retrieve_context`（`infra/knowledge/retrieve.py:22-101`）：

```
1. 参数校验（query / kb_ids / k / char_budget 任一为空即返回 ""）
2. 把 query 也做一次嵌入           embed_knowledge_texts(services, [query])
3. 取当前用户可见的库              owner ∪ shared ∪（admin 时为全部）
4. 对每个选中的 kb_id：
     a. 只取 status == "ready" 且非目录的文档
     b. KnowledgeIndex(kb_id).search(query_vector, k=k)   ← 逐库 top-k
     c. 命中且文档 ready → 收录（带 base/hit/document 三元组）
5. 所有库的命中合并，按 score 降序排序
6. 取全局 top-k
7. 格式化 + 追加引用标记
```

**注意是"每个库各取 top-k，再全局合并取 top-k"**——不是先合并所有 chunk 再排序。库多时，单库的 k 可能挤掉别的库的结果。

### 8.3 相似度算法（⚠️ 性能关键点）

```98:134:src/octop/infra/knowledge/index.py
    def search(self, query_vec: Sequence[float], k: int) -> list[Hit]:
        """Return the ``k`` best chunk hits using in-process cosine similarity."""
        ...
        with self._connect() as conn:
            rows = conn.execute(
                "SELECT chunk_id, doc_id, ordinal, text, embedding, meta_json FROM chunks"
            ).fetchall()
        hits: list[Hit] = []
        for chunk_id, doc_id, ordinal, text, blob, meta_json in rows:
            embedding = struct.unpack(f"<{len(blob) // 4}f", blob)
            if len(embedding) != len(query):
                continue
            norm = math.sqrt(sum(value * value for value in embedding))
            score = (
                0.0
                if norm == 0
                else sum(a * b for a, b in zip(query, embedding, strict=True)) / (query_norm * norm)
            )
            ...
        return sorted(hits, key=lambda hit: hit.score, reverse=True)[:k]
```

- **把该库所有 chunk 全量读进内存**，在 Python 里逐个算余弦相似度
- **没有向量索引**（不是 pgvector / FAISS / HNSW），是**全表扫描 + 纯 Python 计算**
- 每个知识库是独立文件，所以扫描范围限于该库

**影响**：单库 chunk 数上万后，每次检索都会明显变慢，且会把整个库的向量读进内存。这是当前架构的主要性能瓶颈。

### 8.4 上下文格式化与引用

```108:132:src/octop/infra/knowledge/retrieve.py
def _format_context(
    ranked: Sequence[tuple[Any, Hit, Any]], *, char_budget: int, locale: str
) -> str:
    sections: list[str] = []
    remaining = char_budget
    for base, hit, document in ranked:
        citation = tr(

    if not sections:
        return ""
    body = tr("knowledge.retrieval.preamble", locale) + "\n\n" + "\n\n".join(sections)
    return append_citations_marker(body, citations_from_ranked(ranked))
```

- 每段带**引用标记**（库名 + 原始文件名 + 第几段）
- 受 `char_budget`（默认 **6000 字符**）约束，超出就截断/丢弃后面的段
- 末尾用 `append_citations_marker` 附加结构化的引用元数据（供 Dashboard 渲染引用卡片）

### 8.5 返回给模型

工具返回的是一段纯文本（带引用标记）。它作为**工具执行结果**进入对话上下文，模型据此作答。工具描述里明确要求：`Do not invent citations; only use returned passages.`

## 10. 内网部署注意点

| 环节 | 内网要求 |
|------|---------|
| **embedding 模型**（必须） | ONNX 本地模型权重必须预置到 `$OCTOP_HOME/embedding_models/`，或用 `OCTOP_ONNX_COS_BASE` 指向内网镜像。**缺了连建库都失败** |
| OCR（可选） | 需 `rapidocr` / `onnxruntime` / `pymupdf` 三个包（`knowledge-ocr` extra） |
| 远程 embedding（可选） | 需内网可达的 OpenAI 兼容 `/embeddings` 服务 |
| 文档解析 | 纯 Python 库（pypdf / python-docx / python-pptx / openpyxl / xlrd），已随 wheel 安装 |
| 知识库索引 | **始终是本地 SQLite 文件**——即使控制面切到 PostgreSQL 也不变 |
| 磁盘规划 | 每个库一份原始文档 + 一份 index.sqlite；向量体积 ≈ chunk 数 × 维度 × 4 字节 |
