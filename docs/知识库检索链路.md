# 知识库：从上传到检索的完整链路

一份文档从上传到被模型引用，中间经历了哪些步骤、数据落在哪里、对话时怎么被选中和检索。

> **基线**：`1.0.2b4`（`origin/main` = `232030f4`）。文中 `文件:行` 均基于该版本。
> 配套文档：
> - [`docs/存储与记忆机制.md`](./存储与记忆机制.md) —— 整体存储分层
> - [`docs/内网可用性审计.md`](./内网可用性审计.md) —— embedding 模型的内网预置（§5.1 Step 3）

---

## 0. 全流程一图

整个过程可以分成**两个侧**：左半边是「写入侧」（文档怎么进库），右半边是「读取侧」（每次对话怎么用）。

```
┌──────────────────── 写入侧（上传一次，长期有效）────────────────────┐
│ ① 上传    POST /api/knowledge-bases/{kb_id}/documents              │
│             校验：功能是否可用、写权限、大小、扩展名、OCR 开关        │
│ ② 落盘    原始文件 → ~/.octop/knowledge/<kb_id>/docs/<doc_id><后缀> │
│           元数据   → 控制面 DB 的 knowledge_documents（status=pending）│
│ ③ 入队    enqueue_index_document()，进程内异步任务，并发上限 2       │
│ ④ 解析    parse_document() 按扩展名分派                            │
│ ⑤ 分片    chunk_text()  800 字符窗口 / 120 字符重叠                 │
│ ⑥ 嵌入    embed_knowledge_texts()  onnx 本地模型 或 remote API      │
│ ⑦ 建索引  <kb_id>/index.sqlite 的 chunks 表（同事务先删后插）        │
│           元数据   → status=ready, chunk_count=N                    │
└────────────────────────────────────────────────────────────────────┘
┌──────────────────── 读取侧（每轮对话都走一遍）─────────────────────┐
│ ⑧ 选库    三方来源合并 → 本轮挂载的 KB 列表                         │
│ ⑨ 注入    request["configurable"] = {knowledge_base_ids, catalog…}  │
│ ⑩ 改描述  中间件把库名/描述写进 search_knowledge 的工具描述          │
│           （catalog 为空则直接摘除该工具）                           │
│ ⑪ 调用    模型自主决定是否调用 search_knowledge(query, k)           │
│ ⑫ 检索    query 嵌入 → 逐库余弦 top-k → 全局合并排序                │
│ ⑬ 格式化  引用标记 + 正文，受 6000 字符预算裁剪                      │
│ ⑭ 应答    作为工具结果回到模型上下文                                │
└────────────────────────────────────────────────────────────────────┘
```

**最关键的一点先说**：知识库检索是**模型主动发起的工具调用**，不是系统自动把资料塞进提示词。模型能不能检索、知道有哪些库，全靠第 ⑩ 步对工具描述的动态改写。

## 1. 阶段一：上传与落盘

### 1.1 入口

知识库的文档有三个来源：**上传文件**、**在线新建 md/txt**、**编辑已有 md/txt**。另外还有两个重索引入口。

| 操作 | 端点 | 说明 |
|------|------|------|
| 上传文件 | `POST /api/knowledge-bases/{kb_id}/documents` | `UploadFile` + 可选 `path`（用于放进子目录） |
| 新建 md/txt | `POST /api/knowledge-bases/{kb_id}/documents/text` | 直接给文本内容，不经过上传 |
| 编辑 md/txt | `PUT /api/knowledge-bases/{kb_id}/documents/{doc_id}` | 覆盖内容并把状态打回 `pending` |
| 单文档重索引 | `POST .../documents/{doc_id}/reindex` | 只重置状态，等待调度 |
| 整库重索引 | `POST /api/knowledge-bases/{kb_id}/reindex` | 遍历库内所有文档批量入队 |

这五个入口有个共同点：**HTTP 请求只负责"落盘 + 记账 + 入队"，不做解析和嵌入**。真正的重活交给后台任务，所以上传接口很快就会返回，文档状态先是 `pending`。

入队调用点见 `api/routers/knowledge_bases.py:712,750,853,925,956`。

### 1.2 上传时的校验链

`KnowledgeService.upload_document`（`infra/knowledge/service.py:347-391`）在写任何东西之前会依次过六道校验，任何一道不过就直接抛错：

| 顺序 | 校验 | 规则与后果 |
|:---:|------|-----------|
| 1 | **功能可用** | 调用 `assert_knowledge_usable(...)`。没配好 embedding 模型时**连建库/上传都会被拒**（详见 §4） |
| 2 | 写权限 | `get_writable_base` —— 只有 owner 或 admin 能写；`shared` 的知识库对其他人**只读** |
| 3 | 文件大小 | 受 `max_upload_mb` 限制，默认 **100 MiB**（可用 `OCTOP_MAX_UPLOAD_MB` 调整，范围 1–1024） |
| 4 | 图片需 OCR | 后缀是图片（png/jpg/jpeg/webp）但 OCR 没启用 → 直接拒绝，而不是存进来再失败 |
| 5 | 内容类型 | 必须在白名单 `_ALLOWED_CONTENT_TYPES` 内（15 种扩展名映射而来） |
| 6 | 数量上限 | 单库默认最多 **100 篇**（`MAX_DOCS_PER_KB`，库上可调）；单用户最多 **20 个库**（`MAX_BASES_PER_OWNER`） |

这里的设计意图是**尽早失败**：与其把文件存下来、几秒后在后台任务里报错，不如在 HTTP 层就把明显不可能成功的情况挡掉（比如图片没开 OCR、文件类型不支持）。

### 1.3 落盘位置：文件名会被替换成 doc_id

磁盘布局由 `infra/knowledge/files.py` 的三个小函数拼出，逻辑很简单：库目录 → `docs/` 子目录 → 以 doc_id 命名的文件。

```21:23:src/octop/infra/knowledge/files.py
def document_path(kb_id: str, doc_id: str, filename: str) -> Path:
    suffix = Path(filename).suffix.lower()
    return documents_dir(kb_id) / f"{doc_id}{suffix}"
```

注意最后一行的 `f"{doc_id}{suffix}"`：**磁盘上的文件名就是 doc_id 加扩展名，原始文件名不参与**。

最终形成的目录结构：

```
~/.octop/knowledge/<kb_id>/
├── docs/
│   ├── 01J8XT....pdf       ← 文件名是 doc_id
│   ├── 01J8XZ....docx
│   └── 01J8Y1....md
└── index.sqlite            ← 向量索引（见 §5）
```

这个设计带来两个实际影响：

1. **排查问题时到磁盘上找不到原文件名**。你要先查数据库 `knowledge_documents.filename` 拿到 doc_id，才能定位文件。
2. **重命名不需要动文件**。改名只更新数据库里的 `filename`，磁盘文件保持原名不动，所以重命名是廉价的。

元数据（原始文件名、大小、内容类型、状态、分片数）都存在控制面数据库的 `knowledge_bases` / `knowledge_documents` 两张表里 —— 即「文件内容在磁盘、目录结构在数据库」的混合模型。

## 2. 阶段二：解析

解析的目标是**把任意格式的文档变成一段纯文本**，后续所有步骤都在文本上做。入口是 `parse_document(path, ocr=...)`（`infra/knowledge/parse.py:32-71`），它本质上是一个大的扩展名分派表：

| 扩展名 | 解析方式 |
|--------|---------|
| `.md` `.markdown` `.txt` `.rst` `.yaml` `.yml` `.jsonl` | 直接读文本，**编码依次尝试 UTF-8-BOM → GB18030** |
| `.json` | 解析成对象后格式化输出；解析失败则退回原文 |
| `.html` `.htm` | `HTMLParser` 抽文本：跳过 `script`/`style`/`noscript`/`template`，块级标签处换行 |
| `.csv` / `.tsv` | 按分隔符转成「`# 表名` + 制表符分隔的行」 |
| `.pdf` | `pypdf` 逐页 `extract_text()`；**若抽不出文本且启用了 OCR，则整篇回退到 OCR** |
| `.docx` | `python-docx`（有特殊处理，见下） |
| `.pptx` | `python-pptx`，逐页逐形状取 `text` |
| `.xlsx` `.xlsm` | `openpyxl` 只读模式，每个工作表转成「`# 表名` + 制表符行」 |
| `.xls` | `xlrd`，含日期单元格的格式化 |
| `.png` `.jpg` `.jpeg` `.webp` | **OCR**（需启用） |

几个值得说明的细节：

**中文编码的兜底顺序是刻意设计的。** 注释里解释了原因：以前用 `errors='replace'` 解码 UTF-8，结果 Windows 下 GBK 编码的中文文档变成乱码被"成功"写入索引，检索永远命中不到原文。所以现在先试 UTF-8，失败再试 GB18030，最后才强制替换。

**DOCX 不走常规接口。** 一般做法是遍历 `Document.paragraphs`，但那只会取到 `w:body` 的直接子段落，**表格里的文字、内容控件（`w:sdt`）、修订包裹（`w:ins`）、文本框里的文字都会丢失**。所以这里改为直接遍历 XML 里的 `w:p` 和 `w:altChunk` 节点（`parse.py:110-129`），并跳过 `mc:Fallback`（它的内容和 `mc:Choice` 重复）。

**`altChunk` 的展开是个容易漏的点。** 某些转换器生成的 docx 只留一个占位节点，正文实际在嵌入的 HTML 或嵌套 Word 部件里。如果不展开，这部分内容等于没上传。代码会按内容类型分别处理嵌入的 HTML、纯文本、嵌套 docx。

**PDF 的 OCR 回退是"整篇"级别的**，不是逐页判断——只要全文抽出的文本为空，就整体走 OCR。扫描件 PDF 因此能处理，但代价是慢。

## 3. 阶段三：分片

分片要解决的问题是：模型和向量都有长度上限，一篇长文档必须切成小块才能在检索时精确定位。Octop 采用的是**最朴素的固定字符窗口**：

```15:18:src/octop/infra/knowledge/chunk.py
    step = size - overlap
    chunks: list[str] = []
    for start in range(0, len(content), step):
        chunks.append(content[start : start + size])
```

含义很直白：窗口宽 **800 字符**，每次向前移动 `800 - 120 = 680` 字符，于是相邻两块有 120 字符的重叠。最后一块如果不足 800 字符也照常收下。

| 项 | 说明 |
|----|------|
| 默认窗口 | **800 字符**，重叠 **120 字符**，步长 680 |
| 切分依据 | **纯字符窗口**——不按句子、段落、标题或语义边界 |
| 重叠的作用 | 让跨越边界的内容至少在某一块里完整出现，缓解"答案被切断" |
| 可配置 | `knowledge_chunk_size`（100–8000）、`knowledge_chunk_overlap`（0 到 size−1） |
| 调参影响 | **改参数不会自动重分片**——已索引的文档保持原样，必须触发重索引 |

参数从 `settings` 表读取（`infra/knowledge/params.py:48-79`）。有个细节：**越界的值不会报错，而是静默回落到默认值**（比如把 `chunk_size` 设成 50000，实际生效的是 800）。这在排查"为什么改了参数没效果"时容易困惑。

这种分片的取舍很明确：**实现简单、行为可预测**，代价是不理解文档结构。Markdown 的一级标题可能被切在中间，表格可能被拆散，列表项可能跨块。对结构化文档的检索质量不如按标题/段落切分，但也不会出现"某块特别长或特别短"的失控情况。

## 4. 阶段四：嵌入

### 4.1 两条后端路线

分片之后需要把每块文本转成向量。`embed_knowledge_texts(services, texts)`（`infra/knowledge/embed.py:17-38`）按设置分两条路：

| 后端 | 设置值 | 实现与特点 |
|------|--------|-----------|
| **本地 ONNX**（默认） | `knowledge_embedding_backend = "onnx"` | 调 `onnx_service.embed_texts(model, texts)`，本地推理，**完全不需要外网** |
| **远程 API** | `"remote"` | 走指定 provider 的 OpenAI 兼容 `/embeddings` 接口 |

远程路线有几个实现约束：需要 provider 同时配好 `base_url` 和 `api_key`（缺任一就报 "provider is not ready"）；**每批最多 20 条**（`_KNOWLEDGE_EMBEDDING_BATCH_LIMIT`），超出的部分按顺序切片多次请求；最后会校验返回条数与输入条数一致，不一致直接报错——这是为了防止向量与文本错位。

**默认走本地 ONNX 是内网友好的选择**：只要能拿到模型权重，整个过程不需要任何网络。

### 4.2 向量维度会被记录

首次索引成功后，代码会把向量维度写进知识库记录的 `embedding_dim` 字段（`jobs.py:54-57`），作为这个库"用的是多少维模型"的标记。

> **换 embedding 模型必须重索引**，这是硬约束。检索时如果某个 chunk 的向量维度和当前查询向量不一致，它会被**静默跳过**（`index.py:115-116`），既不报错也不提示。表现就是"换了模型后有些文档检索不到了"。正确做法是走 `reindex_all_documents(...)`，它会把全库文档重置为 `pending` 并重新入队。

### 4.3 功能准入：没有模型就没有知识库

这是内网部署最容易踩的坑。知识库功能不是"降级可用"，而是**前置依赖不满足就整体不可用**：

```138:144:src/octop/infra/knowledge/gate.py
def assert_knowledge_usable(settings_get: SettingsGet, provider_repo: Any = None) -> None:
    """Raise a distinguishable runtime error when the capability cannot be used."""
    capability = get_capability(settings_get, provider_repo)
    if not capability["feature_enabled"]:
        raise RuntimeError("knowledge feature is disabled")
    if not capability["prerequisites_ok"]:
        raise RuntimeError("knowledge embedding prerequisites are not satisfied")
```

`assert_knowledge_usable` 被调用的地方包括**创建知识库、上传文档、编辑文档、重索引、以及每次检索**。所以模型权重缺失时，你会在最外层（建库）就被拦住，而不是等到检索才发现。

内网部署必须预置 ONNX 模型权重到 `$OCTOP_HOME/embedding_models/`，或通过 `OCTOP_ONNX_COS_BASE` 指向内网镜像。详见 [`内网可用性审计.md`](./内网可用性审计.md) §5.1 Step 3。

## 5. 阶段五：索引存储

### 5.1 每个知识库一个独立文件

向量索引**不放在控制面数据库里**，而是每个知识库一个独立的 SQLite 文件，和文档内容放在同一个目录下：

```
~/.octop/knowledge/<kb_id>/index.sqlite
```

这个设计的含义是：**即使控制面切到 PostgreSQL，知识库索引依然是本地 SQLite 文件**，不会跟着走。好处是索引与库同生共死、便于单独备份/删除；代价是不能跨机共享（多实例部署时索引不共享）。

库内只有一张表（`infra/knowledge/index.py:40-55`）：

| 列 | 含义 |
|----|------|
| `chunk_id` | 分片主键 |
| `doc_id` | 所属文档——按文档批量替换/删除时的依据 |
| `ordinal` | 分片在文档内的序号（引用时显示"第 N 段"） |
| `text` | 分片原文（**检索命中后直接用它拼上下文，不再回读原文件**） |
| `embedding` | float32 数组的二进制（`struct.pack`） |
| `meta_json` | 附加元数据 |

注意 `text` 是**冗余存储**的：原文既在 `docs/` 里，也在索引里。这样做是为了检索时不必打开原文件重新解析，代价是磁盘占用翻倍。

### 5.2 重建索引是"同事务先删后插"

重新索引一个文档时（比如改了内容、换了模型），代码在一个事务里先删掉该文档的所有旧分片，再插入新分片：

```86:92:src/octop/infra/knowledge/index.py
        with self._connect() as conn:
            conn.execute("DELETE FROM chunks WHERE doc_id = ?", (doc_id,))
            conn.executemany(
                "INSERT INTO chunks(chunk_id, doc_id, ordinal, text, embedding, meta_json) "
                "VALUES (?, ?, ?, ?, ?, ?)",
                rows,
            )
```

因为是同一事务，**不会出现"新分片插了一半、旧分片已经删了"的中间态**——要么全是新的，要么全是旧的。而且删除是按 `doc_id` 精确范围进行的，不会影响库内其他文档。

### 5.3 文档状态机

每篇文档在生命周期里有四种状态，检索端只认最后一种：

| 状态 | 含义 |
|------|------|
| `pending` | 已上传、等待索引。**进程重启后会被自动恢复**（见 5.4） |
| `processing` | 正在解析/嵌入 |
| `ready` | 索引完成，**可被检索**（检索时只收集这个状态的文档） |
| `failed` | 索引失败，原因写在 `error_message`，`chunk_count` 归零 |

失败不会阻塞其他文档：一篇文档失败只是它自己变成 `failed`，库内其余文档照常可用。

### 5.4 调度：线程池 + 并发 2 + 重启恢复

索引是 CPU 和 I/O 密集型工作（解析文档、跑模型推理），所以**不放在事件循环里**，而是 `loop.run_in_executor` 丢进线程池，避免阻塞其他请求。

并发用进程级信号量限制为 **2**（`INDEX_CONCURRENCY`）。这个数字意味着：一次批量导入 50 个文档时，最多同时处理 2 个，其余的排队。内网机器算力有限时，这个上限实际起到了保护作用。

进程重启后，`resume_pending_index_jobs(services)` 会把所有 `pending` 状态的文档重新入队（`jobs.py:82-86`）。所以**上传后立刻重启服务，文档不会丢**，重启后会继续索引。

## 6. 阶段六：对话时如何选中知识库

从这里开始进入「读取侧」。第一个问题是：一个用户可能有很多知识库，这次对话到底该查哪几个？

### 6.1 三个来源

| 来源 | 说明 |
|------|------|
| **Dashboard 显式指定** | 对话请求里直接带 `knowledge_base_ids`（`api/routers/chat/models.py:89-91`） |
| **用户的 `default_open` 偏好** | 该用户标记为"默认打开"的知识库，无需每次手选 |
| **agent 专家级配置** | agent 自己的 `config_json.knowledge_base_ids`，创建/编辑专家时选定 |

### 6.2 合并规则：显式优先，否则默认注入

三条来源的优先级由 `merge_knowledge_base_ids`（`infra/knowledge/default_open.py:11-35`）决定，逻辑只有两个分支：

```24:25:src/octop/infra/knowledge/default_open.py
    if explicit_ids is not None:
        return list(explicit_ids)
```

**只要调用方显式传了列表（哪怕是空列表），就完全以它为准**，不再做任何默认注入。只有当 `explicit_ids` 是 `None`（调用方没传）时，才走下面这条合并路径：

```
本用户 default_open 的库  ∪  agent 专家级 extra_ids（仅限仍然可见的）
```

注意 `default_open` 的筛选条件带了一个**owner 判断**：

```28:30:src/octop/infra/knowledge/default_open.py
    for base in visible_bases:
        if base.default_open and int(base.owner_user_id) == int(owner_user_id):
            selected.append(base.id)
```

也就是说，`default_open` 是**按创建者生效的个人偏好**。别人共享给你的知识库即使他自己标了 `default_open`，也**不会**自动挂到你的对话上——你必须自己显式选。这个设计避免了"别人打开了某个库，结果全公司对话都被注入"的问题。

### 6.3 两个容易踩的坑

**传 `[]` 和不传完全是两回事。** 不传表示"用我的默认设置"，传空数组表示"**本轮一个知识库都不要**"。这是 Dashboard 用来临时关掉知识库的手段，代码注释里也特意标明 `Including [] — Dashboard opt-out`（`api/routers/chat/turn.py:325`）。

**`extra_ids` 会被可见性过滤。** agent 配置的知识库如果被删了或权限变了，检索时会自动剔除，不会报错。

## 7. 阶段七：模型如何"知道"有哪些库

选库完成后的下一个问题是：模型怎么知道这次能查什么？答案是**通过工具描述的动态改写**，而不是 system prompt。

### 7.1 把选中结果写进本轮运行配置

选中的库 ID 列表，连同它们的展示信息，会被写进本轮请求的 `configurable`：

| 键 | 用途 |
|----|------|
| `knowledge_base_ids` | **检索时的实际范围**——工具执行时只允许查这些库 |
| `knowledge_base_catalog` | **给模型看的展示信息**——`[{id, name, description}]` |

`configurable` 是 LangGraph 的运行时上下文，会一路传到工具内部，所以工具执行时能读到本轮的选择——这是"选中"和"执行"之间的传递通道。

### 7.2 关键机制：每次模型调用前改写工具描述

`KnowledgeSearchHintMiddleware`（`infra/knowledge/hint.py:94-113`）是一个 LangChain 中间件，挂在 `wrap_model_call` 上，**每一次模型调用前**都会执行一遍：

1. 从 `configurable` 读出本轮的 `knowledge_base_catalog`
2. 用库名和描述**重写 `search_knowledge` 工具的 description**
3. **若 catalog 为空，直接把 `search_knowledge` 从工具列表里整个移除**

第三步的设计意图写在类文档注释里：

```96:99:src/octop/infra/knowledge/hint.py
    """Rewrite ``search_knowledge`` description with this turn's KB titles/descriptions.

    Hide the tool entirely when nothing is attached — a "do not call" note in
    the schema is weaker than omitting the tool from the model's tool list.
    """
```

含义是：与其在工具说明里写"没挂载知识库时请勿调用"（模型可能不遵守），不如**让这个工具干脆不存在**——从模型看到的工具清单里摘掉，是更强的约束。

改写后的描述长这样（`tools.py:36-53`）：

```
Search the knowledge bases listed below for relevant passages.
Use this tool when the user's question overlaps any of those topics.
Write `query` as a focused search string (key terms, names, synonyms),
not a chat reply. Do not invent citations; only use returned passages.
Attached this turn:
- 报销制度: 公司报销流程与标准
- 产品手册: 产品功能说明
```

**所以模型判断"要不要检索"的依据，就是这段动态描述里的库名和描述。**这也解释了为什么知识库的**描述字段值得认真填写**——它就是模型决定是否检索的主要线索。

另外，描述里明确写了 `Do not invent citations; only use returned passages.`，目的是抑制模型编造引用。

## 8. 阶段八：检索与注入

### 8.1 工具如何拿到本轮上下文

模型决定检索后调用 `search_knowledge(query, k)`（工具定义见 `infra/knowledge/tools.py:74-111`）。工具的第一步是从运行上下文里取出本轮的选择和身份：

```56:66:src/octop/infra/knowledge/tools.py

    user_raw = cfg.get("user")
    if user_raw is None:
        raise ValueError("missing configurable.user")
    user_id = int(user_raw)

        ids = [str(item).strip() for item in raw_ids if str(item).strip()]
```

拿到 `ids` 之后，工具的检索范围就被**锁死在当轮挂载的库**内。这是"去哪个库检索"的最终落点——模型即使想查别的库也做不到，因为范围是运行时注入的，不在模型控制之下。

工具还有一个输入参数 `k`（默认 8，允许 1–20），模型可以按问题复杂度自行调整取回段数。

### 8.2 检索的七个步骤

`retrieve_context`（`infra/knowledge/retrieve.py:22-101`）串联了整条链路：

1. **参数校验**：`query`、`kb_ids`、`k`、`char_budget` 任一为空或非法，直接返回空串（不报错）
2. **嵌入查询**：把 `query` 也过一遍 `embed_knowledge_texts`，得到查询向量
3. **解析可见范围**：取当前用户可见的库（自己的 ∩ 共享的；admin 则是全部）
4. **逐库检索**：对每个选中的库
   - 先筛出该库中 `status == "ready"` 且非目录的文档
   - 调 `KnowledgeIndex(kb_id).search(query_vector, k=k)` 拿到该库的 top-k
   - 命中项必须落在"ready 文档"集合内才收录
5. **合并排序**：把所有库的命中汇总，按相似度分数降序
6. **取全局 top-k**
7. **格式化**：拼成带引用的文本并追加引用元数据

这里有个**容易忽略的语义**：是"**每个库各取 top-k，再合并取 top-k**"，而不是"把所有库的 chunk 合起来排一次序"。差别在于——某个库可能一次性占满全部 k 个名额，把其他库的结果挤出去。库多的时候，检索结果会偏向分数最高的那一两个库。

另外，**检索失败是静默降级的**：整段逻辑包在 `try/except` 里，异常只记一条 warning 日志并返回空串。所以检索出问题时表现为"模型没找到资料"，而不是报错弹窗——排查时要去日志里找 `knowledge retrieval skipped`。

### 8.3 相似度算法：全表扫描 + 纯 Python 余弦（⚠️ 性能关键点）

这是整条链路里最需要关注的实现。检索的相似度计算没有借助任何向量索引：

```108:116:src/octop/infra/knowledge/index.py
        with self._connect() as conn:
            rows = conn.execute(
                "SELECT chunk_id, doc_id, ordinal, text, embedding, meta_json FROM chunks"
            ).fetchall()
        hits: list[Hit] = []
        for chunk_id, doc_id, ordinal, text, blob, meta_json in rows:
            embedding = struct.unpack(f"<{len(blob) // 4}f", blob)
            if len(embedding) != len(query):
                continue
```

它做的是：**把该库所有分片（含向量二进制）一次性读进内存**，逐个反序列化，然后在 Python 里算余弦相似度：

```117:122:src/octop/infra/knowledge/index.py
            norm = math.sqrt(sum(value * value for value in embedding))
            score = (
                0.0
                if norm == 0
                else sum(a * b for a, b in zip(query, embedding, strict=True)) / (query_norm * norm)
            )
```

| 特征 | 现状 |
|------|------|
| 索引结构 | **无**（不是 FAISS / HNSW / pgvector，也没有任何近似最近邻结构） |
| 检索方式 | 全表 `SELECT` → 全量载入内存 → 逐条计算 |
| 计算位置 | Python 解释器（不是向量化运算） |
| 查询复杂度 | O(库内分片数 × 向量维度) |
| 扫描范围 | 限于该知识库（每个库是独立文件，不会扫别的库） |

顺带一提，`if len(embedding) != len(query): continue` 这一行就是 §4.2 提到的"换模型后旧向量被静默跳过"的实现位置。

**影响与判断**：分片数在几百到几千量级时，这个实现完全够用。但**上万分片后，每次检索都会明显变慢**——不仅要遍历全部向量，还要把整个库的 `text` 字段（冗余存储的原文）一起读进内存。这是当前知识库架构的主要性能瓶颈。

若将来要优化，方向是明确的：要么引入 ANN 索引（如 sqlite-vec / hnswlib），要么把向量计算向量化（numpy 批量运算），要么把索引迁到支持向量类型的数据库。但任何一种都会改变"每个库一个 SQLite 文件"这个现有约束，属于架构级改动。

### 8.4 格式化：引用标记 + 字符预算

最后一步是把命中的分片拼成一段文本（`infra/knowledge/retrieve.py:108-132`）。它的核心是**边拼边扣预算**：

```112:126:src/octop/infra/knowledge/retrieve.py
    sections: list[str] = []
    remaining = char_budget
    for base, hit, document in ranked:
        citation = tr(
            "knowledge.retrieval.citation",
            locale,
            name=base.name,
            filename=document.filename,
            ordinal=hit.ordinal + 1,
        )
        if remaining <= len(citation):
            break
        text = hit.text.strip()[: remaining - len(citation)]
        if not text:
            continue
        section = f"{citation}{text}"
```

每一段的结构是「**引用标记** + 正文」，引用标记包含三个信息：**库名**、**原始文件名**（来自数据库，不是磁盘上的 doc_id）、**第几段**（`ordinal + 1`）。

预算控制的规则值得注意：

- 总预算是 `char_budget`，默认 **6000 字符**
- 每拼一段就从剩余预算里扣除该段长度
- **如果剩余预算装不下一条引用标记，直接 `break`**（后面的段全部丢弃，而不是跳过这一段继续尝试）
- 单段文本若超出剩余预算，会被**截断**到刚好放得下

所以最后的段可能被截断，而排在更后面的段可能完全没机会出现。排序是相似度降序，因此"最相关的答不上、次相关的反而完整"这种情况不会发生——被牺牲的总是排在后面的。

拼完之后，正文前面会加上一段本地化的引导语（`knowledge.retrieval.preamble`），末尾则通过 `append_citations_marker` 附上**结构化的引用元数据**：

```131:132:src/octop/infra/knowledge/retrieve.py
    body = tr("knowledge.retrieval.preamble", locale) + "\n\n" + "\n\n".join(sections)
    return append_citations_marker(body, citations_from_ranked(ranked))
```

这份元数据是给前端用的：Dashboard 据此渲染可点击的引用卡片（库名、文件名、段号），而模型看到的是带标记的正文。

### 8.5 最终如何进入对话

工具返回的这段文本，作为**工具调用的执行结果**进入对话上下文——和普通工具调用没有区别。模型基于它作答，并在需要时引用其中的段落。

整条链路到此闭环。需要注意的边界是：**检索结果不会替换用户的原始提问**，也不会常驻在 system prompt 里，它只存在于这一次工具调用的返回值中。所以同一轮对话里模型可以多次检索（换不同的 query），这也正是"让模型自己决定何时查"的设计带来的灵活性。
