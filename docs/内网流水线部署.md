# Octop 内网流水线部署指南

面向**无外网 / 弱外网内网**环境的标准化交付流程：内网自建代码仓库 + CI 流水线 + 制品库 + 镜像库，把「构建 → 测试 → 打包 → 发布 → 部署 → 回滚」固化为可重复执行的流水线。

> 配套阅读：
> - [`docs/内网离线部署.md`](./内网离线部署.md) —— 单机离线包全量打包/安装（首次摆渡、应急恢复）
> - [`docker/README_CN.md`](../docker/README_CN.md) —— 容器化部署细节
> - [`AGENTS.md`](../AGENTS.md) §6 —— 本地质量门禁（`make all`）

## 0. 快速定位

### 0.1 本文解决什么

| 问题 | 之前的做法 | 标准化后 |
|------|-----------|---------|
| 代码怎么进内网 | 手工拷贝/摆渡 | 内网 Git 仓库，一次性导入后走合并请求 |
| 依赖怎么来 | 离线包里打全量 wheel | Nexus 私有源代理 + 一次性预热，CI/目标机在线拉取 |
| 怎么构建 | 构建机手工跑 `offline_pack.sh` | GitLab CI 流水线，提交即触发 |
| 怎么发布 | 手工 scp tar.gz | 制品自动归档到 Nexus，带版本号与校验和 |
| 怎么部署 | 手工解压 + 执行脚本 | CI 部署作业（手动卡点）+ 目标机执行固定脚本 |
| 怎么回滚 | 重新打包重装 | 保留历史 wheel，指定旧版本一条命令回退 |

### 0.2 三种网络模型（先选一种）

| 模型 | 内网可达 | 依赖获取方式 | 适用 |
|------|---------|-------------|------|
| **A. 全隔离** | 完全无外网 | 外网机打包 → 摆渡 → 导入 Nexus（附录 A） | 涉密内网、物理隔离 |
| **B. 单向代理** | 仅可达一个代理/镜像节点 | Nexus 配置 remote proxy，出网节点定时预热 | 多数企业内网（**推荐**） |
| **C. 半隔离** | 构建区可出网，生产区不可 | 构建区直连公网镜像 → 推内网制品库 | 开发测试与生产网络分域 |

本文默认按 **B** 描述，A / C 的差异在对应小节以「模型 A / C 说明」标出。

### 0.3 需要按实际替换的占位符

| 占位符 | 含义 | 示例 |
|--------|------|------|
| `<GIT_HOST>` | 内网 Git 服务地址 | `gitlab.corp.local` |
| `<NEXUS_HOST>` | 制品库地址 | `nexus.corp.local:8081` |
| `<HARBOR_HOST>` | 镜像仓库地址 | `harbor.corp.local` |
| `<TARGET_HOST>` | Octop 部署目标机 | `10.0.0.21` |
| `<OCTOP_VERSION>` | Octop 版本（取自 `pyproject.toml`） | `1.0.2b4` |

## 1. 目标架构

### 1.1 角色与组件

```
┌─────────────────────────── 内网（无外网 / 仅可达代理）────────────────────────────┐
│                                                                                 │
│   开发者 ──push──► GitLab CE ──触发──► GitLab Runner                            │
│   (<GIT_HOST>)        │                    │                                    │
│                       │                    ├─ verify : ruff / mypy / pytest     │
│                       │                    ├─ build  : npm build + uv build     │
│                       │                    ├─ package: wheel → Nexus           │
│                       │                    │           image → Harbor          │
│                       │                    └─ deploy : SSH 目标机（手动卡点）    │
│                       │                                                         │
│                  Nexus OSS ◄────────────────┘                                   │
│                  (<NEXUS_HOST>)      pypi-group / npm-proxy / raw               │
│                       ▲                                                         │
│  出网节点（可访问公网或腾讯云镜像）                                                 │
│    └─ 预热：pypi.org / registry.npmjs.org ──缓存──► Nexus proxy                  │
│                                                                                 │
│                  Harbor ◄──── CI 推镜像 ────► 基础镜像预热（node/python/uv）      │
│                                                                                 │
│                  Octop 目标机 (<TARGET_HOST>)                                    │
│                    ├─ 形态一：venv + systemd（pip 从 Nexus 拉依赖）               │
│                    └─ 形态二：docker pull + compose                              │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 1.2 组件清单

| 组件 | 推荐选型 | 作用 | 备注 |
|------|---------|------|------|
| 代码仓库 | GitLab CE（或 Gitea） | 源码托管、MR、CI 编排、变量管理 | GitLab CE 自带 CI，最省事 |
| CI Runner | GitLab Runner（docker executor） | 执行流水线作业 | 需预热 CI 基础镜像到 Harbor |
| 制品库 | Nexus Repository OSS 3 | PyPI/npm/raw 代理与托管 | 一个实例覆盖全部语言生态 |
| 镜像仓库 | Harbor | 镜像存储、漏洞扫描、签名 | 无容器需求时可省略 |
| 构建缓存 | Runner 本地 volume / Nexus raw | 加速 `node_modules`、`.venv` | 可选 |

> **最小可用集合**：GitLab + Runner + Nexus 三件套即可跑通。Harbor 仅在采用容器化部署时需要。
> **更轻替代**：Gitea + Gitea Actions（兼容 GitHub Actions 语法）或 Jenkins，流水线脚本逻辑与本文一致，只需替换 `.gitlab-ci.yml` 的语法外壳。

### 1.3 与现有离线脚本的关系

现有三件套不废弃，职责重新划分：

| 脚本 | 标准化后的定位 |
|------|---------------|
| `scripts/offline_pack.sh` | 模型 A 的摆渡打包器；也是 Nexus 冷启动预热的来源 |
| `scripts/offline_install.sh` | 目标机首次安装的执行体，被 CI 部署脚本调用 |
| `scripts/offline_update.sh` | 目标机增量升级的执行体，被 CI 部署脚本调用 |
| `make build` / `make all` | CI 质量与构建阶段直接复用，不重复实现 |

## 2. 阶段一：环境准备

### 2.1 机器清单

| 角色 | 数量 | 建议配置 | 说明 |
|------|------|---------|------|
| Git 服务 | 1 | 4C / 8G / 200G | 可与其他服务合设 |
| CI Runner | 1~N | 8C / 16G / 200G（构建前端吃内存） | 单机即可起步，`concurrent` 建议 2~4 |
| Nexus | 1 | 4C / 8G / 500G | 依赖缓存会持续增长，磁盘给足 |
| Harbor | 1 | 4C / 8G / 500G | 无容器部署可省 |
| Octop 目标机 | 1~N | 4C / 8G / 100G | 生产机；数据库与工作区都在本地 |
| 出网节点 | 1 | 2C / 4G | 模型 B/C 的代理出口；模型 A 用外网机构建 |

**操作系统基线**（与 [`docs/内网离线部署.md`](./内网离线部署.md) §1 一致）：

| 项 | 要求 |
|----|------|
| 目标机 OS | Linux，**glibc ≥ 2.28**（manylinux_2_28 下限） |
| 目标机架构 | x86_64 或 aarch64 |
| 目标机编译工具 | 必须装 `gcc`（`crcmod`、`evdev` 为 sdist，需现场编译） |
| 镜像构建机 | 需 Docker 20.10+ / BuildKit |

### 2.2 版本矩阵（必须对齐，禁止漂移）

来源：[`mise.toml`](../mise.toml)、[`docker/Dockerfile`](../docker/Dockerfile)、[`.github/workflows/ci.yml`](../.github/workflows/ci.yml)

| 工具 | 版本 | 依据 |
|------|------|------|
| Python | **3.12** | CI matrix、`pyproject.toml` `requires-python` |
| Node.js | **20** | Dockerfile、release workflow |
| npm | **10** | 随 Node 20 附带 |
| uv | **0.7.x**（建议固定） | Dockerfile 使用 `ghcr.io/astral-sh/uv:0.7` |
| PostgreSQL（可选） | 16 + pgvector | `docker/docker-compose.postgres.yml` |
| gcc | ≥ 7.3 | 目标机编译 sdist |

> **铁律**：Runner 与目标机的 Python/Node 版本必须与上表一致。版本漂移会直接导致「CI 能过、目标机装不上」。

### 2.3 步骤 A：部署 Git 服务与 Runner

**A-1 安装 GitLab CE**（内网离线安装包方式，模型 A/B 通用）

```bash
# 在内网 Git 服务器上，使用预先摆渡的 gitlab-ce 离线包安装
sudo rpm -Uvh gitlab-ce-<version>-ce.0.el8.x86_64.rpm      # RHEL 系
sudo gitlab-ctl reconfigure

# 配置 external_url
sudo sed -i 's|^external_url.*|external_url "http://<GIT_HOST>"|' /etc/gitlab/gitlab.rb
sudo gitlab-ctl reconfigure
```

**A-2 注册 Runner**

```bash
# 在 Runner 机器上（需 Docker）
docker run -d --name gitlab-runner --restart always \
  -v /srv/gitlab-runner/config:/etc/gitlab-runner \
  -v /var/run/docker.sock:/var/run/docker.sock \
  gitlab/gitlab-runner:latest

docker exec -it gitlab-runner gitlab-runner register \
  --non-interactive \
  --url "http://<GIT_HOST>" \
  --token "<项目或群组 Runner Token>" \
  --executor "docker" \
  --docker-image "<HARBOR_HOST>/ci/octop-ci:python3.12-node20" \
  --docker-pull-policy "if-not-present" \
  --docker-volumes /var/run/docker.sock:/var/run/docker.sock \
  --docker-volumes /cache
```

> executor 选 **docker**：环境干净、可复现。基础镜像见 §2.7。
> 挂载 `/var/run/docker.sock` 是为了 `package:image` 作业能在容器内执行 `docker build` / `docker push`（`privileged` 仍可保持 `false`）。
> 若内网无法拉取 `gitlab/gitlab-runner` 镜像，先用容器化部署前提把该镜像导入 Harbor（附录 A §A.3）。

**A-3 Runner 调优**（`/srv/gitlab-runner/config/config.toml`）

```toml
concurrent = 4
[[runners]]
  executor = "docker"
  [runners.docker]
    privileged = false
    volumes = ["/cache", "/var/run/docker.sock:/var/run/docker.sock"]
  [runners.cache]
    Type = "local"
```

### 2.4 步骤 B：部署 Nexus 制品库

**B-1 创建仓库**（Nexus 控制台 → Repository → Create）

| 仓库名 | 类型 | 上游 / 说明 |
|--------|------|------------|
| `pypi-proxy` | pypi (proxy) | `https://mirrors.cloud.tencent.com/pypi/simple`（或 `https://pypi.org/simple`） |
| `pypi-hosted` | pypi (hosted) | 存放 Octop 自建 wheel |
| `pypi-group` | pypi (group) | 成员：`pypi-proxy` + `pypi-hosted`，**对外统一地址** |
| `npm-proxy` | npm (proxy) | `https://registry.npmmirror.com`（或 `https://registry.npmjs.org`） |
| `npm-group` | npm (group) | 成员：`npm-proxy` + 自建 npm 包（如有） |
| `raw-hosted` | raw (hosted) | 存放离线包、部署脚本、校验和 |

对外访问地址形如：

```
PyPI : http://<NEXUS_HOST>/repository/pypi-group/simple
npm  : http://<NEXUS_HOST>/repository/npm-group/
raw  : http://<NEXUS_HOST>/repository/raw-hosted/
```

**B-2 客户端统一配置**

Runner 与目标机都需要能解析到 Nexus。推荐在系统级落配置，避免每条命令传参：

```bash
# /etc/pip.conf
[global]
index-url = http://<NEXUS_HOST>/repository/pypi-group/simple
trusted-host = <NEXUS_HOST>
timeout = 60

# ~/.npmrc（或 CI 变量 npm_config_registry）
registry=http://<NEXUS_HOST>/repository/npm-group/
strict-ssl=false
```

```bash
# CI 变量（GitLab → Settings → CI/CD → Variables）
UV_INDEX_URL      = http://<NEXUS_HOST>/repository/pypi-group/simple
UV_INSECURE_HOST  = <NEXUS_HOST>          # HTTP 或自签证书时必需
PIP_INDEX_URL     = http://<NEXUS_HOST>/repository/pypi-group/simple
PIP_TRUSTED_HOST  = <NEXUS_HOST>
npm_config_registry = http://<NEXUS_HOST>/repository/npm-group/
```

> `UV_INDEX_URL` + `uv sync --frozen` 的组合是本项目 Dockerfile 已在用的方式（见 `docker/Dockerfile` 第 105-110 行），可安全沿用。
> 若后续升级 uv 后遇到 `lockfile 与 index 不一致` 报错，退回「`uv export` + `pip`」路线：与 `scripts/offline_pack.sh` 第 204-221 行完全一致。

### 2.5 步骤 C：部署 Harbor（容器化部署时必需）

1. 安装 Harbor（离线安装包），项目 `library` 之外的私有项目建 `ci/`、`octop/`。
2. 所有节点 `/etc/docker/daemon.json` 配置 insecure-registry：

```json
{
  "insecure-registries": ["<HARBOR_HOST>"],
  "registry-mirrors": ["http://<HARBOR_HOST>"]
}
```

3. 推送凭据写入 CI 变量 `HARBOR_USER` / `HARBOR_PASSWORD`。

### 2.6 步骤 D：依赖预热（**最关键的一步**）

流水线能否跑通，取决于 Nexus 是否已缓存全部依赖。预热只做一次，后续增量缓存。

**D-1 Python 依赖预热**（在出网节点或可访问 Nexus proxy 的机器上）

```bash
cd /opt/octop-src          # 内网仓库的一份检出
uv export --frozen --no-dev --extra browser --no-emit-project --no-hashes \
  -o /tmp/requirements.txt

# 指向 Nexus group：命中则直接返回，未命中则 proxy 回源并缓存
python3.12 -m pip download -r /tmp/requirements.txt \
  --index-url http://<NEXUS_HOST>/repository/pypi-group/simple \
  --trusted-host <NEXUS_HOST> \
  -d /tmp/warmup-pypi

# 目标机架构的依赖（若目标机是 aarch64 而预热机是 x86_64）
python3.12 -m pip download -r /tmp/requirements.txt \
  --platform manylinux_2_28_aarch64 --python-version 3.12 \
  --implementation cp --abi cp312 --only-binary=:all: \
  --index-url http://<NEXUS_HOST>/repository/pypi-group/simple \
  --trusted-host <NEXUS_HOST> \
  -d /tmp/warmup-pypi-aarch64
```

**D-2 前端依赖预热**

```bash
cd dashboard
npm ci --registry http://<NEXUS_HOST>/repository/npm-group/
```

**D-3 基础镜像预热**（模型 A/B 都需要）

```bash
for img in node:20-slim python:3.12-slim ghcr.io/astral-sh/uv:0.7 \
           pgvector/pgvector:pg16 gitlab/gitlab-runner:latest; do
  docker pull "$img"
  docker tag  "$img" "<HARBOR_HOST>/ci/$(basename "$img" | tr ':' '-')"
  docker push "<HARBOR_HOST>/ci/$(basename "$img" | tr ':' '-')"
done
```

> 使用 `docker/Dockerfile` 构建镜像时，把 `FROM node:20-slim` 等改为 `FROM <HARBOR_HOST>/ci/node-20-slim`，或直接在 daemon 配置 `registry-mirrors` 让 Docker 自动改写。

**模型 A 说明**：先在外网机执行 `bash scripts/offline_pack.sh` 生成全量离线包，摆渡进内网后按附录 A 把 wheelhouse 导入 `pypi-hosted`。

### 2.7 步骤 E：构建 CI 基础镜像

流水线作业需要 Python / Node / gcc / uv 齐备。把它做进一个镜像，避免每次作业重装工具链。

新建 `deploy/ci/Dockerfile`：

```dockerfile
# CI 基础镜像：内含流水线所需全部工具链
# 构建：docker build -f deploy/ci/Dockerfile -t <HARBOR_HOST>/ci/octop-ci:python3.12-node20 .
FROM <HARBOR_HOST>/ci/python-3.12-slim

ENV PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    UV_LINK_MODE=copy \
    UV_PYTHON_DOWNLOADS=never

# 目标机侧编译 sdist 需要 gcc；CI 侧用于构建工具
# openssh-client：部署作业需要 scp/ssh/ssh-keyscan
# docker.io（或 docker-ce-cli）：package:image 作业需要 docker build/push
RUN apt-get update && apt-get install -y --no-install-recommends \
        gcc build-essential libffi-dev git curl ca-certificates \
        openssh-client docker.io \
    && rm -rf /var/lib/apt/lists/*

# Node 20（从 Harbor 预热的构建器阶段拷贝，或改用 Nexus 分发的 nodejs 包）
COPY --from=<HARBOR_HOST>/ci/node-20-slim /usr/local /usr/local

# uv 0.7（固定版本，避免漂移）
COPY --from=<HARBOR_HOST>/ci/uv-0.7 /uv /uvx /usr/local/bin/
```

```bash
docker build -f deploy/ci/Dockerfile -t <HARBOR_HOST>/ci/octop-ci:python3.12-node20 .
docker push <HARBOR_HOST>/ci/octop-ci:python3.12-node20
```

### 2.8 环境准备验收

```bash
# 1. Nexus 能解析 PyPI 依赖
curl -sI http://<NEXUS_HOST>/repository/pypi-group/simple/fastapi/ | head -1   # 200

# 2. Nexus 能解析 npm 依赖
curl -sI http://<NEXUS_HOST>/repository/npm-group/react | head -1              # 200

# 3. Runner 在线（GitLab → Settings → CI/CD → Runners 显示绿色）
docker exec gitlab-runner gitlab-runner verify

# 4. CI 基础镜像可用
docker run --rm <HARBOR_HOST>/ci/octop-ci:python3.12-node20 \
  bash -lc "python -V && node -v && npm -v && uv --version && gcc --version | head -1"
```

## 3. 阶段二：代码入库

### 3.1 首次导入

**方式一：`git bundle`（推荐，保留完整提交历史）**

```bash
# 外网开发机
git bundle create octop-<date>.bundle --all

# 摆渡到内网后
git clone octop-<date>.bundle octop
cd octop && git remote set-url origin http://<GIT_HOST>/infra/octop.git
git push -u origin --all && git push origin --tags
```

**方式二：直接在内网初始化**（不需要历史时）

```bash
git init && git add -A && git commit -m "chore: initial import"
git remote add origin http://<GIT_HOST>/infra/octop.git
git push -u origin main
```

**方式三：模型 C（构建区可出网）** 可直接在构建区 `git clone` 外网仓库，推送到内网 Git。

### 3.2 分支模型与保护规则

| 分支 | 用途 | 保护规则 |
|------|------|---------|
| `main` | 生产发布分支 | 禁止直推；必须 MR；CI 全绿；1 人审批 |
| `develop` | 集成分支 | 禁止直推；CI 全绿 |
| `release/x.y` | 版本冻结线（可选） | 禁止直推 |
| `feature/*` | 特性开发 | 无保护 |

打标签发布：`v1.0.2b4` → 触发发布流水线（与 `.github/workflows/release.yml` 语义一致）。

### 3.3 代码同步铁律

内网仓库是**唯一事实源**。外网 → 内网的同步必须满足：

1. **单向**：只允许外网 → 内网推送，禁止内网 → 外网（防泄漏）。
2. **带标签**：同步时同步 tag，保证内网能打出与外网一致的版本号。
3. **不手改版本号**：`pyproject.toml` 的 `version` 由外网决定，内网只消费。
4. **同步即验证**：同步后立即跑一次流水线，确认可构建。

> 若内网需要独立发版（本地补丁），走 `release/*` 分支 + `version` 后缀（如 `1.0.2b4.corp1`），不要污染 `main`。

### 3.4 仓库内需要新增的文件

```
.gitlab-ci.yml                  # 流水线定义
deploy/
  ci/Dockerfile                 # CI 基础镜像
  install.sh                    # 目标机首次安装（CI 调用）
  update.sh                     # 目标机升级（CI 调用）
  rollback.sh                   # 目标机回滚（CI 调用）
  docker-compose.prod.yml       # 容器化部署编排
  octop.env.example             # 生产环境变量样例
```

> `Makefile`、`scripts/offline_*.sh` 不需要修改，流水线直接复用。

## 4. 阶段三：CI 流水线

### 4.1 阶段划分

```
verify ──► build ──► package ──► deploy(manual)
  │         │          │            ├─ staging（自动）
  │         │          │            └─ production（手动卡点）
  │         │          └─ wheel → Nexus pypi-hosted / image → Harbor
  │         └─ 前端产物 + uv build
  └─ ruff / mypy / pytest（对齐 make lint / typecheck / test）
```

| 阶段 | 触发条件 | 产物 | 门禁 |
|------|---------|------|------|
| `verify` | 每次 MR / push | 无 | 必须全绿，否则阻断合并 |
| `build` | `main` / tag | `octop-<version>-py3-none-any.whl` | 构建失败即失败 |
| `package` | `main` / tag | Nexus 制品 + Harbor 镜像 | 上传失败即失败 |
| `deploy` | tag / 手动 | 目标机上的新版本 | 部署后健康检查通过 |

### 4.3 制品命名与版本规范

| 制品 | 命名 | 说明 |
|------|------|------|
| wheel | `octop-<version>-py3-none-any.whl` | 名字由 `pyproject.toml` 决定，**不要手工改名** |
| wheel 校验 | `octop-<version>-py3-none-any.whl.sha256` | 部署前校验 |
| 构建标记 | `<version>+<commit-sha>` | 仅用于 Nexus 目录/镜像 tag，不写入 wheel metadata |
| 镜像 | `<HARBOR_HOST>/octop/octop:<version>` + `:latest` | 与 tag 对应 |

> **为什么不能改 wheel 文件名**：wheel 名内嵌版本，改名会导致 `pip` 元数据与实际不符，`octop --version` 与制品不一致。构建标记只放在制品库路径或镜像 tag 上。

### 4.4 CI 常见坑

| 现象 | 原因 | 处理 |
|------|------|------|
| `uv sync` 报 lockfile 与 index 不一致 | uv 版本升级改变了 index 语义 | 固定 uv 0.7.x；或改用 `uv export` + `pip install -r` |
| `npm ci` 失败「lock 与 package.json 不一致」 | 外网改了 `package.json` 未同步 lock | 外网 `npm install` 后提交 `package-lock.json` |
| 构建期 OOM（前端 vite） | Runner 内存不足 | 设 `NODE_OPTIONS=--max-old-space-size=1024`，或加内存 |
| 作业拉不到基础镜像 | Harbor 未预热 | 执行 §2.6 D-3 |
| `pip download` 拿不到 aarch64 包 | 未指定 `--platform` | 按 §2.6 D-1 加 platform 参数 |
| 页面 404（部署后） | 前端产物缺失 | 确认 `make build` 先生成 `src/octop/dashboard/index.html` |

## 5. 阶段四：部署

### 5.1 形态选择

| 形态 | 适用 | 优点 | 代价 |
|------|------|------|------|
| **venv + systemd** | 无容器平台、需精细控制 | 与现有离线方案完全一致，升级只换 wheel | 需编译 sdist（gcc） |
| **Docker + Compose** | 有 Harbor / 容器平台 | 依赖固化在镜像，环境一致 | 镜像较大，需镜像仓库 |

> 两者都支持 `~/.octop/` 数据目录分离，升级不丢数据。

### 5.2 目标机准备（一次性）

```bash
# 1. 专用账号
sudo useradd -m -s /bin/bash octop

# 2. 编译工具（sdist 需要）
sudo yum install -y gcc      # 麒麟 / RHEL 系
sudo apt-get install -y gcc  # Debian 系

# 3. 部署免密（CI → 目标机）
#    在 CI 侧生成密钥对，公钥写入目标机 octop 用户
sudo -u octop mkdir -p /home/octop/.ssh && sudo chmod 700 /home/octop/.ssh
echo "<CI 部署公钥>" | sudo -u octop tee -a /home/octop/.ssh/authorized_keys
sudo chmod 600 /home/octop/.ssh/authorized_keys

# 4. 提权规则：注册 systemd 服务需要写 /etc/systemd/system
#    仅放行 octop 命令，避免给部署账号完整 root
echo 'octop ALL=(ALL) NOPASSWD: /home/octop/.octop/bin/octop' | sudo tee /etc/sudoers.d/octop >/dev/null
sudo chmod 440 /etc/sudoers.d/octop

# 5. pip 指向内网 Nexus
sudo tee /etc/pip.conf >/dev/null <<'EOF'
[global]
index-url = http://<NEXUS_HOST>/repository/pypi-group/simple
trusted-host = <NEXUS_HOST>
timeout = 60
EOF

# 6. 开放防火墙（跨机访问）
sudo firewall-cmd --permanent --add-port=8088/tcp && sudo firewall-cmd --reload
```

### 5.3 首次部署（systemd 形态）

新建 `deploy/install.sh`：

```bash
#!/usr/bin/env bash
# 目标机首次安装 —— 从内网 Nexus 拉依赖，无需离线包
set -euo pipefail

OCTOP_HOME="${OCTOP_HOME:-/home/octop/.octop}"
VERSION="${1:?用法: install.sh <version> 例如 1.0.2b4}"
PYPI_INDEX="${PYPI_INDEX:-http://<NEXUS_HOST>/repository/pypi-group/simple}"
PYPI_HOST="${PYPI_HOST:-<NEXUS_HOST>}"

info() { printf '\033[0;32m[deploy]\033[0m %s\n' "$*"; }

# 1. 解释器（目标机自带 python3.12，或用 uv 装的独立解释器）
PY_BIN="${PY_BIN:-python3.12}"
command -v "$PY_BIN" >/dev/null || { echo "缺少 python3.12"; exit 1; }

# 2. venv
mkdir -p "$OCTOP_HOME"
"$PY_BIN" -m venv "$OCTOP_HOME/venv"
VIP="$OCTOP_HOME/venv/bin/pip"
"$VIP" install --quiet --upgrade pip setuptools wheel

# 3. 从内网 Nexus 安装 octop（依赖一并解析）
info "安装 octop==$VERSION"
"$VIP" install --quiet \
  --index-url "$PYPI_INDEX" --trusted-host "$PYPI_HOST" \
  "octop==$VERSION"

# 4. CLI 包装
mkdir -p "$OCTOP_HOME/bin"
cat > "$OCTOP_HOME/bin/octop" <<WRAP
#!/usr/bin/env bash
set -euo pipefail
export OCTOP_HOME="\${OCTOP_HOME:-$OCTOP_HOME}"
exec "\$OCTOP_HOME/venv/bin/octop" "\$@"
WRAP
chmod +x "$OCTOP_HOME/bin/octop"

# 5. 初始化（已有数据库则跳过）
if [ ! -f "$OCTOP_HOME/octop.db" ]; then
  info "初始化数据库与管理员"
  OCTOP_HOME="$OCTOP_HOME" "$OCTOP_HOME/bin/octop" init --yes \
    --admin-username "${OCTOP_ADMIN_USERNAME:-admin}" \
    --admin-password "${OCTOP_ADMIN_PASSWORD:?首次安装必须设置 OCTOP_ADMIN_PASSWORD}"
fi

# 6. 注册并启动系统服务（跨机访问绑 0.0.0.0）
#    注：--scope system 需要 root（sudoers 已放行）；若以普通用户 sudo 执行，systemd 会
#    安装 user unit，需额外 `loginctl enable-linger <user>` 才能开机自启。
info "注册 systemd 服务"
sudo "$OCTOP_HOME/bin/octop" service start \
  --host 0.0.0.0 --port "${OCTOP_PORT:-8088}" --scope system

info "完成: $("$OCTOP_HOME/bin/octop" --version)"
```

> 已有离线包时，把第 3 步替换为 `scripts/offline_install.sh --bundle ...`，其余不变。

### 5.5 自动升级

新建 `deploy/update.sh`（CI 调用；也可手工执行）：

```bash
#!/usr/bin/env bash
# Octop 升级：可选本地 wheel，或直接从内网 Nexus 拉指定版本
set -euo pipefail

OCTOP_HOME="${OCTOP_HOME:-/home/octop/.octop}"
WHEEL=""
VERSION=""
PYPI_INDEX="${PYPI_INDEX:-http://<NEXUS_HOST>/repository/pypi-group/simple}"
PYPI_HOST="${PYPI_HOST:-<NEXUS_HOST>}"

while [ $# -gt 0 ]; do
  case "$1" in
    --wheel)   WHEEL="${2:-}"; shift 2 ;;
    --version) VERSION="${2:-}"; shift 2 ;;
    *) echo "未知参数: $1"; exit 1 ;;
  esac
done

VIP="$OCTOP_HOME/venv/bin/pip"
[ -x "$VIP" ] || { echo "未找到已安装的 Octop，请先执行 install.sh"; exit 1; }

OLD="$("$OCTOP_HOME/bin/octop" --version 2>/dev/null || echo 未知)"
echo "[deploy] 当前版本: $OLD"

# 升级前备份（数据可回滚）
"$OCTOP_HOME/bin/octop" backup create -o "/tmp/octop-backup-$(date +%Y%m%d-%H%M%S).tar.gz" || true

if [ -n "$WHEEL" ]; then
  [ -f "${WHEEL}.sha256" ] && ( cd "$(dirname "$WHEEL")" && sha256sum -c "$(basename "$WHEEL").sha256" --quiet )
  "$VIP" install --quiet --no-index --no-deps --force-reinstall "$WHEEL"
  [ -n "$VERSION" ] || VERSION="$(basename "$WHEEL" | sed -E 's/^octop-(.*)-py3-none-any\.whl$/\1/')"
else
  [ -n "$VERSION" ] || { echo "需要 --wheel 或 --version"; exit 1; }
  "$VIP" install --quiet --upgrade \
    --index-url "$PYPI_INDEX" --trusted-host "$PYPI_HOST" "octop==$VERSION"
fi

NEW="$("$OCTOP_HOME/bin/octop" --version 2>/dev/null || echo 未知)"
sudo "$OCTOP_HOME/bin/octop" service restart || true

# 健康检查（最多重试 12 次 × 5s）
PORT="$(sed -n 's/.*"port"[: ]*\([0-9]\+\).*/\1/p' "$OCTOP_HOME/config.json" 2>/dev/null | head -1)"
PORT="${PORT:-8088}"
for i in $(seq 1 12); do
  if curl -sf -m 5 "http://127.0.0.1:${PORT}/api/health" >/dev/null; then
    echo "[deploy] 升级成功: $OLD -> $NEW"
    exit 0
  fi
  sleep 5
done

echo "[deploy] 健康检查失败，请查看 $OCTOP_HOME/logs/octop.log" >&2
exit 1
```

> `--no-deps` 仅在依赖未变时安全。依赖有变化（`pyproject.toml` / `uv.lock` 改动）时，改用 `--version` 走 Nexus 全量解析，或走 `scripts/offline_install.sh` 全量安装。

### 5.6 回滚

```bash
# 方式一：回退到指定历史版本（Nexus 上仍有该版本）
bash deploy/update.sh --version <上一个版本>

# 方式二：从 Nexus raw 仓库取历史 wheel
curl -u "$NEXUS_USER:$NEXUS_PASSWORD" -O \
  "http://<NEXUS_HOST>/repository/raw-hosted/octop/backup/octop-<旧版本>-py3-none-any.whl"
bash deploy/update.sh --wheel ./octop-<旧版本>-py3-none-any.whl

# 方式三：数据层回滚（仅在数据被破坏时）
"$OCTOP_HOME/bin/octop" backup restore /tmp/octop-backup-<时间戳>.tar.gz --yes
```

**回滚注意事项**：数据库迁移是**向前**的。若新版本执行了 schema 迁移，代码回退可能遇到「表结构比代码新」。此时优先回退到上一个包含相同迁移的版本；跨大版本回滚前必须先用 `octop backup create` 备份。

### 5.7 部署验收

```bash
# 目标机上
~/.octop/bin/octop --version                      # 版本号与本次发布一致
ss -ltnp | grep 8088                              # 应为 0.0.0.0:8088
curl -s http://127.0.0.1:8088/api/health          # {"ok":true,"db":true,...}
curl -s http://127.0.0.1:8088/api/setup/status
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8088/   # 200
sudo systemctl status octop --no-pager | head -5  # active (running)

# 另一台机器上（跨机连通性）
curl -s http://<目标机IP>:8088/api/health
```

> 判定逻辑：**本机 curl 通、跨机不通 → 一定是监听地址（`bind_host`）或防火墙问题**，与 Octop 本身无关。

### 6.3 故障速查

| 现象 | 排查顺序 |
|------|---------|
| 升级后服务起不来 | `tail -n 100 ~/.octop/logs/octop.log`；确认依赖是否变更（`--no-deps` 是否误用） |
| 跨机访问不通 | ① `ss -ltnp \| grep 8088` 是否 `0.0.0.0:8088`；② 防火墙；③ 网络 ACL |

| 页面 404 | 前端产物缺失，重建（`make build`）后重新发布 |
| 编译 `crcmod` / `evdev` 失败 | 目标机缺 gcc（`yum install -y gcc`） |
| `GLIBC_2.28 not found` | 目标机 glibc < 2.28，需升级系统 |
| 磁盘满 | Nexus blob 存储 / 日志 / `~/.octop` 数据库增长，清理历史制品 |

    || echo "跳过（可能已存在）: $f"
done

  --repository-url "http://<NEXUS_HOST>/repository/pypi-hosted/" \

### B. `config.json` 关键字段

```json
{
  "bind_host": "0.0.0.0",
  "port": 8088,
  "enable_api_docs": false,
  "uni_auth": {
    "enabled": false
  }
}
```

| 字段 | 说明 |
|------|------|
| `bind_host` | 跨机访问必须为 `0.0.0.0`；默认 `127.0.0.1` 仅本机可访问 |
| `port` | 默认 8088 |
| `enable_api_docs` | `/api/docs`（Scalar）开关，默认关闭 |
| `uni_auth` | 内网统一认证（CMS 单点登录），详见 [`内网离线部署.md`](./内网离线部署.md) §10 |

### C. 系统服务与防火墙

```bash
# 服务管理（systemd 由 octop 自动生成 unit）
sudo ~/.octop/bin/octop service start  --host 0.0.0.0 --port 8088 --scope system
sudo ~/.octop/bin/octop service status
sudo ~/.octop/bin/octop service restart
sudo ~/.octop/bin/octop service stop

# 防火墙
sudo firewall-cmd --permanent --add-port=8088/tcp && sudo firewall-cmd --reload   # firewalld
sudo ufw allow 8088/tcp                                                          # ufw
```

> SELinux 一般无需调整（Octop 是普通进程）。若怀疑被拦，可临时 `sudo setenforce 0` 验证。
